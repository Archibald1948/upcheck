## 포트를 셋으로 나눈 이유

| 포트 | 무엇 | 기본 노출 |
|---|---|---|
| 3000 | 상태 페이지 (Next.js) | **호스트에 공개** |
| 8484 | 공개 API | compose 내부만 |
| 8485 | 운영 (metrics·pprof) | `127.0.0.1` (compose 안에서는 내부만) |

pprof 는 힙 내용과 모든 goroutine 스택을 내보낸다. 지표는 모니터 이름과 내부
구조를 드러낸다. 공개 API 와 **같은 포트에 두면 안 되는** 것들이다.

실제로 확인했다.

```
$ curl http://localhost:8484/debug/pprof/     → 404   (공개 API 에 없음)
$ curl http://localhost:8484/metrics          → 404
$ curl http://localhost:8484/api/status       → (컨테이너에서는 호스트에 아예 안 열림)
```

## 완료 기준 점검 — 스펙 6절 전부

### 1. 모니터 100개를 오래 돌려도 goroutine 이 늘지 않음

`/metrics` 의 `go_goroutines` 를 14초마다 긁었다.
모니터 100개 · 2초 주기 · 응답 200ms · 150초 구동.

```
경과   goroutine  체크수
  14s        39       573
  28s        40      1129
  42s        39      1681
  56s        39      2233
  70s        39      2793
  84s        39      3353
  98s        39      3905
 112s        39      4465
 126s        39      5017
 140s        39      5569
```

체크를 5,900회 가까이 하는 동안 **39개에서 평평하다**(28초의 40은 스크레이프
goroutine 하나). Go 1.27의 새 프로파일도 확인했다.

```
$ curl "http://127.0.0.1:8485/debug/pprof/goroutineleak?debug=1"
goroutineleak profile: total 0
```

"아무도 깨워줄 수 없는 goroutine" 이 **0개**다. 전체 goroutine 수를 눈으로
세는 것보다 판정이 명확하다.

### 2. down 알림 정확히 1회, 복구 시 up 1회

M3에서 실제로 서버를 죽였다 살려서 확인했다 → [11](11-M3-알림.md).

### 3. 플래핑에 알림 폭탄이 없음

60초 동안 상태가 20번 뒤집히는 엔드포인트에 알림 3건(쿨다운 20초 기준),
29건 억제 → [11](11-M3-알림.md).

### 4. Ctrl+C 시 5초 내 종료

| 경우 | 소요 |
|---|---|
| 로컬 SIGTERM | **0.02초** |
| `docker compose stop` (두 컨테이너) | **1.44초** · 종료 코드 0 |

컨테이너 로그에 종료 요약까지 찍힌다. `ENTRYPOINT` 를 exec 형식으로 써서
upcheck 가 PID 1 로 SIGTERM 을 직접 받기 때문이다.

### 5. `go test -race ./...` 통과

9개 패키지 전부 통과.

### 6. 상태 페이지에서 90일 업타임 바가 렌더됨

M5에서 실제 브라우저로 확인했고 → [14](14-M5-API와-상태페이지.md),
M6에서는 **compose 스택을 통해** 다시 확인했다.

```
$ curl -s http://localhost:3000/ | ...
  HTTP OK, 길이 239201
  업타임 바: 9 개
  배너: 일부 시스템에 장애가 있습니다
  시간대 표기: True
```

### 7. `docker compose up` 한 방으로 뜸

```
$ docker compose up -d
 Container upcheck-upcheck-1  Started
 Container upcheck-upcheck-1  Waiting
 Container upcheck-upcheck-1  Healthy

SERVICE   STATUS                    PORTS

```

`upcheck` 가 healthy 가 된 뒤에 `web` 이 뜬다. distroless 이미지에서
바이너리가 스스로 헬스체크를 수행한 결과다.

## 부딪힌 것들

### 1. /metrics 가 기존 코드의 전제를 깼다

`collector` 와 `alert.Engine` 의 통계는 평범한 `int64` 였다. M2·M3 당시에는
"Run 이 끝난 뒤에만 읽는다"는 전제였고 주석에도 그렇게 적어 뒀다.

`/metrics` 스크레이프는 **다른 goroutine** 에서 그 값을 읽는다. 전제가 깨졌다.
`atomic.Int64` 로 바꿨다. `go test -race` 가 있어서 바로 드러나는 종류다.

> 기능을 하나 붙일 때 기존 코드의 **전제**가 여전히 참인지 확인해야 한다.
> 주석에 적어 둔 전제는 특히 쉽게 낡는다.

### 2. pprof 는 import 만으로 전역 mux 를 오염시킨다

"공개 API 에 pprof 가 안 붙었는지" 보는 테스트를 `DefaultServeMux` 에 대고
썼더니 **실패**했다. `net/http/pprof` 의 `init()` 이 blank import 든 아니든
`DefaultServeMux` 에 핸들러를 등록하기 때문이다.

막을 방법이 없으므로, 지켜야 할 규칙은 **어디서도 `DefaultServeMux` 를
서비스하지 않는 것**이다. `http.ListenAndServe(addr, nil)` 한 줄이면
그 포트에 프로파일이 전부 열린다.

테스트를 "공개 API 핸들러가 `/debug/pprof/` 에 404 를 준다"로 바꿨다.
**틀린 주석을 테스트가 잡아낸 경우다.**

### 3. 인증서 남은 일수를 문자열에서 파싱할 뻔했다

M4 에서는 남은 일수가 `Detail`·`Warning` 문자열에만 있었다. 지표로 내보내려면
숫자가 필요해서 처음엔 정규식으로 뽑으려 했다. 문구를 손보는 순간 조용히 깨진다.
`Result.CertDaysLeft *int` 필드를 추가했다.

> 화면에 보여줄 문자열과 계산에 쓸 값은 따로 들고 있어야 한다.
> M4에서 `Detail`(표시)과 `Warning`(경고)을 나눈 것의 연장이다.

### 4. distroless 에서만 깨질 뻔한 것들

로컬에서는 멀쩡한데 컨테이너에서만 실패하는 것들이라 미리 처리했다.

- **시간대**: `/usr/share/zoneinfo` 가 없어 `LoadLocation("Asia/Seoul")` 이 실패한다
  → `import _ "time/tzdata"`
- **데이터 디렉터리**: `mkdir` 도 `chown` 도 없다
  → 빌드 단계에서 만들어 소유권째 복사
- **헬스체크**: `curl` 도 셸도 없다
  → 바이너리에 `-healthcheck` 모드

실제로 compose 로 띄워 `Asia/Seoul` 날짜가 제대로 나오는 것까지 확인했다.

```
timezone: Asia/Seoul · 날짜 ['2026-09-14', '2026-09-15', '2026-09-16']
```

### 5. 버전이 컨테이너에서 `(devel)` 로 나온다

`.dockerignore` 가 `.git` 을 제외해서 `debug.ReadBuildInfo()` 가 커밋 해시를
못 찾는다. 로컬 빌드에서는 `5a9f52b-dirty` 로 잘 나온다.

빌드 컨텍스트를 가볍게 하는 쪽을 택했고, 커밋 해시가 필요하면
`.git` 을 포함시키거나 빌드 인자로 넘기면 된다. 알고 둔 절충이다.

### 되짚어 보면 이어지는 결정들

- **M2에서 순수 Go SQLite 드라이버**를 고른 것이 → M6에서 `CGO_ENABLED=0`
  정적 바이너리 → **27MB distroless 이미지**로 이어졌다
- **M5에서 브라우저가 Go API 를 직접 부르지 않게** 한 것이 → M6에서 API 포트를
  **호스트에 열지 않는** compose 구성으로 이어졌다
- **M1에서 결과 채널 소비자를 하나로** 둔 것이 → M2의 SQLite 쓰기 직렬화를
  공짜로 만들었고 → M3의 판정 엔진이 붙을 자리가 됐다
- **M3의 Notifier 인터페이스**가 → M4의 Prober → M5의 `http.Handler` 로
  같은 모양이 반복됐다

### 반복해서 나온 교훈

1. **추측하지 말고 재라.** M1의 스케줄러 선택, M2의 롤업 효과, M6의 goroutine
   안정성까지 전부 숫자로 확인했다. "노란 칸이 많아 보인다"고 의심했던 건
   세어 보니 난수 분산이었다.
2. **통과하는 테스트가 옳은 것을 보는지 확인하라.** M4의 인증서 만료 테스트는
   `EOF` 때문에 통과하고 있었다.
3. **정확한 값과 근사값을 구분해서 전달하라.** 업타임은 롤업 후에도 정확하고
   백분위수는 근사다. 숨기지 않고 `Approx` 로 표시한다.
4. **기록과 알림은 다르다.** 쿨다운으로 알림이 억제돼도 장애 이력은 남는다.
5. **0과 "데이터 없음"은 다르다.** 업타임 0%는 "완전히 죽어 있었다"는 뜻이다.
6. **에러 메시지는 내부 구조를 흘린다.** 공개 API 는 기본으로 감춘다.

## 여기서 더 간다면

스펙의 M0~M6은 끝났다. 실제로 본인 서비스에 붙여 쓰면서 이어갈 만한 것들:

- **`checks_hourly` 를 일별로 한 번 더 접기** — 90일 넘게 보관하려면
- **알림 채널 추가** — `Notifier` 를 구현하면 끝이다 (텔레그램, 이메일)
- **경고를 알림으로** — 인증서 만료 임박은 지금 화면에만 뜬다.
  `Kind` 에 `KindWarn` 을 추가하고 별도 쿨다운을 두면 된다
- **모니터를 API 로 추가/삭제** — 지금은 YAML 이 원본이다
- **여러 지역에서 체크** — 한 곳에서만 보면 그 네트워크의 문제와 구분되지 않는다
