# 08 — M1: 동시성과 스케줄러 선택

## 스펙이 던진 과제

> **설계 결정 지점**: 모니터마다 `time.Ticker` 를 하나씩 두는 방식 vs 중앙 스케줄러 + 워커풀.
> 전자는 코드가 짧고 후자는 확장성이 좋습니다.
> **둘 다 짜보고** 왜 후자를 골랐는지 README에 쓰세요.
> — `go-upcheck.md` M1

그래서 둘 다 구현했다. 고른 건 워커풀인데, **이유를 글이 아니라 측정으로** 정리한다.

| 구현 | 파일 | 쓰는 법 |
|------|------|---------|
| 중앙 스케줄러 + 워커풀 | `internal/scheduler/pool.go` | `-scheduler pool` (기본) |
| 모니터당 Ticker goroutine | `internal/scheduler/ticker.go` | `-scheduler ticker` |

둘 다 같은 인터페이스를 만족한다.

```go
type Scheduler interface {
    Run(ctx context.Context, monitors []config.Monitor) <-chan checker.Result
    Name() string
    Stats() Stats
}
```

## 두 구조

### A. 모니터당 Ticker (`ticker.go`)

```
모니터 1 ──> goroutine + Ticker ──┐
모니터 2 ──> goroutine + Ticker ──┼──> results ──> collector
모니터 N ──> goroutine + Ticker ──┘
```

코드가 확실히 짧다. 큐도, 워커풀도, "진행 중" 추적도 필요 없다.
모니터마다 자기 주기로 알아서 돌면 그만이다. 핵심이 20줄이다.

```go
func (t *TickerScheduler) loop(ctx context.Context, m config.Monitor, results chan<- checker.Result) {
    ticker := time.NewTicker(m.Interval())
    defer ticker.Stop()
    for {
        res := t.checker.Check(ctx, m)
        select {
        case results <- res:
        case <-ctx.Done():
            return
        }
        select {
        case <-ctx.Done():
            return
        case <-ticker.C:
        }
    }
}
```

### B. 중앙 스케줄러 + 워커풀 (`pool.go`)

```
스케줄러 goroutine 1개
   │  tick 마다 "때가 된 모니터" 를 훑어서
   ↓
 jobs (버퍼 채널, 크기 = workers × 2)
   ↓
워커 goroutine N개
   ↓
 results ──> collector
```

goroutine 수가 **모니터 수와 무관하게 N+2 로 고정**된다.

## 측정

같은 조건에서 둘을 돌렸다. 동시 요청 수는 클라이언트 코드를 읽어서 추정한 게 아니라
**서버가 직접 센 값**이다 (`cmd/slowserver` 의 `/stats`).

```bash
go run ./cmd/slowserver -delay 200ms     # 터미널 1
go run ./cmd/upcheck -config configs/bench-50.yaml -scheduler pool -duration 11s -quiet
curl -s localhost:8080/stats             # 터미널 2
```

### 정상 부하 — 모니터 50개, 주기 5초, 응답 200ms, workers 8

요구 10건/초 vs 풀 용량 40건/초. 여유가 있다.

| | pool | ticker |
|---|---|---|
| **서버가 관측한 최대 동시 요청** | **3** | **50** |
| 체크 횟수 (11초) | 108 | 150 |
| 큐가 가득 차 미룸 | 0 | — |
| 최대 지연 | 201ms | — |

두 방식 다 일은 해낸다. 차이는 **부하의 모양**이다.

- **ticker**: t=0, 5, 10초에 50개를 한꺼번에 때린다. 뾰족한 스파이크 3번.
- **pool**: 시작 시각을 주기 안에 고르게 흩어서(stagger) 초당 10건씩 평평하게 흘린다.

같은 양의 일을 하면서 **상대 서버가 받는 순간 부하는 17분의 1**이다.
감시 대상이 내 서비스라면, 모니터링이 만드는 스파이크가 그 자체로 부하다.

### 과부하 — 모니터 50개, 주기 1초, 응답 500ms, workers 8

요구 50건/초 vs 풀 용량 16건/초. 일부러 3배 넘게 밀어 넣었다.

| | pool | ticker |
|---|---|---|
| **서버가 관측한 최대 동시 요청** | **8** (= workers) | **50** |
| 최대 goroutine | 29 | **154** |
| 서버가 받은 총 요청 | 160 | 500 |
| 체크된 모니터 | 50 / 50 | 50 / 50 |
| 과부하를 알려주는가 | **그렇다** (미룸 612, 건너뜀 187, 최대지연 2.65초) | **아니다** (0, 0, 0) |
| 종료 후 남은 goroutine | **3** | 23 |

> 숫자는 실행마다 조금씩 흔들린다. 자릿수와 방향이 요점이다.

여기서 갈린다.

**1. 동시성에 상한이 있는가**

pool 은 정확히 `workers` 만큼만 나간다. ticker 는 `workers` 설정을 아예 무시한다.
모니터 1000개를 등록하면 1000개가 동시에 나간다.
스펙 5절 규칙 3번이 금지한 바로 그것이다.

**2. 과부하를 알 수 있는가**

이게 더 중요하다. ticker 의 통계는 전부 0이다. 문제가 없어서가 아니라
**셀 자리가 없어서**다. `time.Ticker` 의 채널 버퍼는 1이라, 체크가 주기보다
오래 걸리면 밀린 tick 이 **조용히 버려진다**. 어디에도 기록되지 않는다.

pool 은 큐에 못 넣을 때마다 세고 로그를 남긴다.

```
스케줄러: 예약 169 · 큐가득미룸 612 · 진행중건너뜀 187 · 최대지연 2.652s
  → 큐가 가득 찬다. workers 를 늘리거나 interval 을 늘려야 한다.
  → 체크가 주기보다 오래 걸린다. timeout_ms 나 interval_sec 을 점검하자.
```

모니터링 도구가 자기 상태를 모르면 곤란하다.

**3. 종료 후에 무엇이 남는가**

ticker 로 돌린 뒤 남은 goroutine 스택을 떠 봤다.

```
goroutine profile: total 41
35 @ ...
#	net.(*Resolver).lookupIPAddr+0x2f7	net/lookup.go:343
#	net/http.(*Transport).dialConn+0x667	net/http/transport.go:1920
```

35개가 **DNS 조회에 묶여 있었다.** `lookupIPAddr` 은 context 로 취소해도
실제 질의 goroutine 이 남는다. OS 리졸버 호출을 중간에 끊을 수 없어서다.

동시에 50개를 띄웠으면 취소 못 하는 잔여물도 50개분 남는다.
위 표에서 종료 후 남은 goroutine 이 3개 대 23개로 갈린 게 이것이다.
**동시성 상한은 종료 시점의 뒷정리에도 영향을 준다.** 예상 못 한 소득이었다.

## 그래서 pool

| 기준 | pool | ticker |
|------|:----:|:------:|
| 코드 길이 | 길다 | **짧다** |
| goroutine 수 | **워커 수 고정** | 모니터 수 비례 |
| 동시 요청 상한 | **있다** | 없다 |
| 부하 분산 | **고르게 편다** | 주기마다 스파이크 |
| 과부하 가시성 | **센다 + 로그** | 조용히 버린다 |
| 모니터별 다른 주기 | 가능 | 가능 |
| 종료 후 잔여물 | **적다** | 많다 |
| 동적 추가/삭제 (M5) | 슬라이스만 갱신 | goroutine 생성/종료 관리 필요 |

ticker 가 이기는 칸은 "코드 길이" 하나다.
**모니터가 10개면 ticker 로 충분하다.** 하지만 이 프로젝트의 목표가
"수백 개 엔드포인트를 동시에 감시"이므로 pool 을 고른다.

ticker 구현은 지우지 않고 남겨 둔다. 비교 대상이 없으면
위 표는 그냥 주장이고, 있으면 측정이다.

## 구현하면서 부딪힌 것들

### 1. 시작 시각을 흩어야 한다 (stagger)

처음엔 모든 모니터의 첫 실행을 `now` 로 뒀다. 결과:

```
스케줄러: 예약 72 · 큐가득버림 78 · ...
```

**예약보다 버린 게 많았다.** 50개가 같은 순간에 몰려 큐(16칸)가 즉시 넘쳤고,
주기가 같으니 그 뒤로도 계속 같이 몰렸다.

각자의 주기 안에 고르게 펴서 해결했다.

```go
offset = monitors[i].Interval() * time.Duration(i) / time.Duration(n)
next[i] = now.Add(offset)
```

부하가 시간축에 평평해지면서 **같은 워커 수로 훨씬 많은 모니터를 감당**한다.
정상 부하 실험에서 동시 요청이 8이 아니라 3까지 떨어진 게 이 효과다.

분산이 의미를 가지려면 tick 이 그보다 촘촘해야 해서 기본 tick 도 1초 → 250ms 로 줄였다.

### 2. 밀린 모니터가 굶었다

과부하 실험에서 **50개 중 42개만** 체크됐다. 8개는 한 번도 못 받았다.

원인은 두 가지가 겹쳤다.
- 매 tick 마다 모니터를 **인덱스 순서대로** 훑어서 앞쪽이 큐를 먼저 차지했다
- 큐에 못 넣어도 `next[i]` 를 다음 주기로 **밀어버려서**, 밀린 모니터가
  "밀렸다"는 사실조차 잃고 뒤쪽으로 계속 밀려났다

고친 방법:

```go
// 가장 오래 밀린 것부터 처리한다
slices.SortFunc(pending, func(a, b dueItem) int {
    return a.due.Compare(b.due)
})
```

그리고 큐에 못 넣었을 때는 `next` 를 **갱신하지 않는다.**
다음 tick 에도 밀린 상태로 남아 정렬에서 앞자리를 차지한다.
결과: **50/50**. 테스트로 고정해 뒀다 (`TestPoolChecksEveryMonitor`).

> 그래서 통계 이름도 `Dropped`(버림) → `Deferred`(미룸)로 바꿨다.
> 체크를 버리는 게 아니라 다음 tick 으로 미루는 것이고,
> 같은 모니터가 여러 번 세어진다. 절대값이 아니라 **0이냐 아니냐**를 봐야 한다.

### 3. 분산을 너무 넓게 했더니 첫 결과가 안 나왔다

실제 사이트 설정(주기 60초, 모니터 6개)으로 8초만 돌려 봤더니
**6개 중 4개만** 결과가 나왔다.

시작 시각을 **주기 전체**에 걸쳐 흩었기 때문이다. 인덱스가 뒤쪽인 모니터는
첫 오프셋이 `60초 × 4/6 = 40초` 라서 8초 안에 차례가 오지 않았다.
부하 분산만 보면 맞는 계산인데, **기동 직후 현황을 볼 수 없다**는 게 문제다.
주기가 60초인 모니터의 첫 결과를 1분 가까이 기다리는 건 모니터링 도구로서 낙제다.

분산 구간에 상한을 둬서 해결했다.

```go
w := min(monitors[i].Interval(), maxStaggerWindow)  // maxStaggerWindow = 5초
offset = w * time.Duration(i) / time.Duration(n)
```

이제 이 값이 곧 **"기동 후 모든 모니터의 첫 결과가 나오기까지 걸리는 최대 시간"** 이다.
주기가 짧으면(벤치의 5초) 여전히 주기 전체에 걸쳐 흩어지므로 위 측정값은 그대로다.

순간적으로 몰리더라도 워커풀이 상한을 걸고, 밀린 것부터 처리하니
큰 문제가 되지 않는다는 판단이다. 부하 분산과 기동 반응성의 절충이고,
**둘 중 후자를 택했다**는 걸 상수 하나에 적어 뒀다.

### 4. 왜 tick + 훑기인가 (힙이 아니라)

모니터 1000개를 250ms 마다 훑으면 초당 비교 4000번이다. 사실상 공짜다.
"다음 실행 시각 최소 힙 + 정확한 타이머"가 이론적으로는 낫지만,
코드가 훨씬 복잡해지는 값을 이 규모에서는 못 한다.
수만 개가 되면 그때 바꾸면 된다.

### 5. 종료 순서

채널을 닫는 주체를 명확히 해야 한다 (스펙 5절 규칙 2번).

```
ctx 취소
  → 스케줄러가 반환 → defer close(jobs)
      → 워커들이 jobs 에서 ok==false 를 받고 반환
          → wg.Wait() 풀림 → close(results)
              → main 의 for range 종료
```

`for range results` 가 끝났다는 건 **내부 goroutine 이 전부 반환했다**는 뜻이다.
호출부는 이 한 줄로 종료 완료를 알 수 있다.

| 기준 | 상태 |

| Ctrl+C 시 5초 내 종료 | `TestShutdownIsPrompt` — 3초 응답 서버 상대로 **1ms 미만** |

```bash

```
