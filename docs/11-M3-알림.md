# 11 — M3: 알림

## 스펙이 요구한 것

> - **상태 전이에만** 발송 (up→down, down→up). 매 체크마다 보내면 안 됩니다.
> - **플래핑 방지**: 연속 N회 실패해야 down으로 확정 (기본 3회)
> - **쿨다운**: 같은 모니터에 대해 X분 내 재발송 금지
> - 채널: Discord 웹훅, Slack 웹훅 (인터페이스로 추상화해서 나중에 추가 가능하게)
> — `go-upcheck.md` M3

## 만든 것

```
internal/alert/
├── alert.go       Event · Notifier 인터페이스 · Rules
├── engine.go      상태 전이 판정 (M3의 핵심)
├── dispatcher.go  별도 goroutine 에서 발송
├── webhook.go     Discord · Slack
└── setup.go       설정 → 규칙 + 발송기

internal/store/incidents.go   장애 이력 (M2에서 만든 테이블을 채운다)
```

흐름은 이렇다.

```
scheduler → results → collector ─┬→ SQLite (체크 기록)
                                 └→ Engine (판정)
                                       ├→ SQLite (장애 이력)
                                       └→ Dispatcher 큐 ──> goroutine ──> 웹훅
```

**판정과 발송을 버퍼 채널로 끊어 놓은 게 핵심이다.** 스펙 7절 함정이다.

> 알림 발송이 체크 루프를 블로킹 → 별도 goroutine + 버퍼 채널.
> 알림 서버가 느려도 모니터링은 계속돼야 함.

## 3단 관문

`Engine.maybeNotify` 가 세 관문을 차례로 통과시킨다.

```go
// 관문 1: 아직 확정 안 됨 — 알릴 게 없다.
if st.confirmed == statusUnknown { return }

// 관문 2: 이미 알린 상태와 같다 — 새 소식이 아니다.
if st.confirmed == st.notified { return }

// 관문 3: 쿨다운.
if !st.notifiedAt.IsZero() && now.Sub(st.notifiedAt) < e.rules.Cooldown {
    e.suppressed++
    return
}
```

### 관문 1 — 임계치 (플래핑 1차 방어)

연속 `FailureThreshold` 회 실패해야 `statusDown` 으로 **확정**한다.
1회 실패로는 상태가 바뀌지 않는다. 일시적인 네트워크 끊김 하나로
사람을 깨우지 않기 위한 것이다.

```go
switch {
case st.consecutiveFail >= e.rules.FailureThreshold:
    st.confirmed = statusDown
case st.consecutiveOK >= e.rules.SuccessThreshold:
    st.confirmed = statusUp
}
// 둘 다 아니면 이전 확정 상태를 유지한다.
```

`default` 로 `statusUnknown` 을 주지 않는 게 중요하다.
실패 1회로는 "아직 down 이 아니지만 그렇다고 up 도 아닌" 상태인데,
여기서 상태를 지워버리면 확정 이력이 날아간다.

### 관문 2 — 상태 전이만

`confirmed`(실제 상태)와 `notified`(마지막으로 알린 상태)를 **따로** 들고 있다.
둘이 같으면 보낼 게 없다. 스펙의 "매 체크마다 보내면 안 됩니다"가 이 한 줄이다.

기동 직후 첫 확정이 `up` 이면 조용히 넘어간다.
"잘 돌고 있다"는 알림거리가 아니다. 반대로 **기동 시점에 이미 죽어 있으면 알린다.**

```go
if st.notified == statusUnknown && st.confirmed == statusUp {
    st.notified = statusUp
    return   // notifiedAt 은 일부러 갱신하지 않는다
}
```

`notifiedAt` 을 갱신하지 않는 게 미묘한 부분이다. 갱신하면 기동 직후
발생한 장애가 쿨다운에 걸려 억제된다. 제로값으로 두면
`now.Sub(zeroTime)` 이 수백 년이라 쿨다운을 자연히 통과한다.

### 관문 3 — 쿨다운 (플래핑 2차 방어)

억제할 때 **`st.notified` 를 갱신하지 않는다.** 이게 설계의 핵심이다.

그래서 쿨다운이 끝난 뒤 다음 체크가 오면 다시 관문 2에서
`confirmed != notified` 가 되어 **그때의 실제 상태**를 보낸다.

- 알림을 **잃는 게 아니라 미룬다**
- 미룬 사이에 상태가 원래대로 돌아갔으면 보낼 것도 없어진다
- 보낼 때는 항상 **현재 상태**를 보낸다 (낡은 알림이 안 나간다)

`TestCooldownDelaysButDoesNotLose` 가 이걸 고정한다.

> **절충**: 쿨다운이 종류를 가리지 않아서, 장애 직후 빠르게 복구되면
> 복구 알림이 쿨다운만큼 늦는다. 스펙이 "같은 모니터에 대해 X분 내
> 재발송 금지"라고 못 박았으므로 그대로 따랐다. 복구를 빨리 알고 싶으면
> `cooldown` 을 줄이면 된다. 늦어질 뿐 사라지지는 않는다.

## 측정 — 스펙 완료 기준

### "down 알림이 정확히 1회, 복구 시 up 알림 1회"

실제로 서버를 죽였다 살렸다.

```bash
# 45초 구동: 10초 정상 → 서버 kill → 15초 down → 서버 복구
```

```
체크 45회 · 모니터 1개
알림: 판정 2건 · 쿨다운 억제 0건 · 발송 2 · 실패 0 · 큐넘침 0

[14:53:50] 장애 발생: 대상 서비스 :: 사유: dial tcp [::1]:8090: connect: connection refused
[14:54:03] 복구됨: 대상 서비스 :: 장애 지속 시간: 14초
```

15초 동안 12번 넘게 실패했지만 알림은 **down 1회 + up 1회**.

### "플래핑에 알림 폭탄이 발생하지 않음"

`cmd/slowserver` 의 `/flaky`(3초 주기로 200 ↔ 503)를 1초마다 체크했다.

```
60초 구동 · 쿨다운 20초

체크 60회 · 모니터 1개
알림: 판정 3건 · 쿨다운 억제 29건 · 발송 3 · 실패 0 · 큐넘침 0

[14:52:23] 장애 발생: 플래핑 서비스
[14:52:44] 복구됨: 플래핑 서비스 :: 장애 지속 시간: 4초
[14:53:05] 장애 발생: 플래핑 서비스
```

60초 동안 상태가 20번 뒤집혔는데 알림은 **3건**, 정확히 쿨다운 간격이다.
`TestFlappingDoesNotStorm` 은 10분 × 600회 체크로 같은 걸 검증한다 — **2건**.

## 인터페이스 — 채널 추가하기

스펙이 명시한 모양 그대로다.

```go
type Notifier interface {
    Notify(ctx context.Context, ev Event) error
    Name() string
}
```

Discord 와 Slack 은 "JSON 을 POST 한다"는 점이 같고 **본문 모양만** 다르다.
그래서 공통부를 `webhook` 구조체에 두고 본문 만들기만 함수로 갈아끼웠다.

```go
type webhook struct {
    name    string
    url     string
    client  *http.Client
    payload func(Event) any   // ← 이것만 다르다
}

func NewDiscord(url string) *webhook {
    return &webhook{name: "discord", url: url, client: newWebhookClient(), payload: discordPayload}
}
```

새 채널(이메일, 텔레그램)을 추가하려면 `payload` 함수 하나만 쓰면 된다.
`Engine` 과 `Dispatcher` 는 손댈 필요가 없다 — 그게 인터페이스의 값이다.

### 반환 타입이 `*webhook` 인 이유

```go
func NewDiscord(url string) *webhook   // Notifier 가 아니라 구체 타입
```

"**Accept interfaces, return structs**" (→ [03](03-메서드와-인터페이스.md)).
받을 때는 넓게 받고 돌려줄 때는 구체적으로 준다.
호출부가 필요하면 알아서 인터페이스에 담는다.

### HTTP 클라이언트를 따로 쓰는 이유

```go
func newWebhookClient() *http.Client { ... }
```

`checker` 의 클라이언트를 재사용하지 않는다. 모니터링 트래픽과 알림 트래픽이
커넥션 풀을 공유하면 서로 영향을 준다. 감시 대상이 많아 풀이 포화되면
알림이 못 나가는 상황이 생긴다.

## Dispatcher — 절대 막지 않는다

```go
func (d *Dispatcher) Send(ev Event) bool {
    select {
    case d.events <- ev:
        return true
    default:
        d.dropped.Add(1)
        return false
    }
}
```

논블로킹 전송이다 (→ [06](06-동시성-기초.md)의 `select` + `default`).
여기서 기다리면 판정 → collector → 스케줄러까지 줄줄이 멈춘다.
**알림 몇 개를 잃는 것보다 모니터링이 멈추는 게 훨씬 나쁘다.**

`TestSendNeverBlocks` 가 1시간짜리 느린 채널을 상대로 Send 100회가
즉시 끝나는지 확인한다.

### ctx 를 보지 않는 goroutine

```go
func (d *Dispatcher) Run(ctx context.Context) {
    for ev := range d.events {
        d.dispatch(ev)
    }
}
```

이 루프는 **ctx 취소로 빠져나오지 않는다.** 다른 goroutine 과 반대다.

종료 중에도 큐에 남은 알림은 보내야 하기 때문이다.
"서비스가 죽었다"는 알림을 프로그램 종료하느라 잃으면 곤란하다.
대신 발송마다 자체 시한을 걸어 무한정 매달리지는 않는다.

```go
ctx, cancel := context.WithTimeout(context.Background(), d.timeout)
```

`context.Background()` 에서 새로 시작하는 게 요점이다.
취소된 ctx 의 자식을 만들면 태어나자마자 취소되어 있다.
(M2의 마지막 배치 저장과 같은 패턴 → [10](10-M2-저장과집계.md))

### 종료 순서

```
ctx 취소
  → 스케줄러 정리 → results 닫힘
      → collector.Run 반환  (= 더 이상 결과가 없다 = Engine 이 이벤트를 안 만든다)
          → dispatcher.Close()   ← 그제서야 채널을 닫는다
              → Run 이 큐를 마저 비우고 반환
```

보내는 쪽(Engine)이 확실히 끝난 뒤에 닫아야 한다 (스펙 5절 규칙 2번).
`TestDispatcherDrainsOnClose` 가 종료 시 큐가 비워지는지 검증한다.

## 알림과 이력은 별개다

```go
// 확정 상태가 바뀌었으면 장애 이력을 남긴다.
// 알림을 실제로 보냈는지와 무관하게 기록한다.
if st.confirmed != prev {
    e.recordIncident(ctx, res, st, prev)
}
e.maybeNotify(st, res, target)
```

**알림은 사람을 깨우는 것이고, 이력은 사실의 기록이다.**
쿨다운으로 알림이 억제돼도 "무슨 일이 있었는가"는 남아야 한다.
`TestIncidentRecordedEvenWhenSuppressed` 가 알림 1건 / 이력 2건 상황을 고정한다.

장애 시작 시각도 **확정 시점(3번째 실패)이 아니라 첫 실패 시각**으로 남긴다.
실제로 죽기 시작한 때가 그때이기 때문이다.

```go
if st.consecutiveFail == 0 {
    st.firstFailAt = res.CheckedAt   // 이번 연속 실패의 첫 번째
}
```

## 부딪힌 것들

### 1. 재시작하면 알림이 다시 갔다

상태 맵은 메모리에만 있다. 프로그램을 재시작하면 비어 있어서,
계속 죽어 있는 서비스에 대해 **같은 장애로 알림이 또 간다.**
배포가 잦거나 크래시 루프에 빠지면 그 자체가 알림 폭탄이 된다.

DB에 열려 있는 장애를 읽어 상태를 복원해 해결했다.

```go
func (e *Engine) Restore(ctx context.Context) error {
    for name, id := range e.ids {
        inc, err := e.store.OpenIncidentFor(ctx, id)
        ...
        e.states[name] = &monitorState{
            confirmed: statusDown, notified: statusDown,
            notifiedAt: e.now(),  // 재시작 직후 즉시 재발송하지 않도록
            downSince: inc.StartedAt,
        }
    }
}
```

`OpenIncident` 도 이미 열린 장애가 있으면 새로 만들지 않게 했다.
`TestRestoreSkipsDuplicateAlert` 로 고정.

### 2. 같은 장애가 두 자리에서 다르게 보였다

알림은 "14초", `-report` 는 "15s". 같은 값인데 한쪽은 `int(d.Seconds())` 로
**버림**, 다른 쪽은 `Duration.Round` 로 **반올림**했기 때문이다.

```go
func humanDuration(d time.Duration) string {
    d = d.Round(time.Second)   // 먼저 반올림하고 나눈다
    sec := int(d.Seconds())
    ...
}
```

사소하지만, 같은 사건의 숫자가 화면마다 다르면 도구를 못 믿게 된다.

### 3. 웹훅 주소를 시작할 때 검증하지 않으면

환경변수를 안 넣으면 `"${UPCHECK_DISCORD_WEBHOOK}"` 이 그대로 주소가 된다.
그러면 **장애가 났을 때 처음** 발송 실패를 알게 된다. 최악의 타이밍이다.

기동 시점에 걸러낸다.

```go
if strings.Contains(raw, "${") || strings.Contains(raw, "$") {
    return fmt.Errorf("alerts.%s: 환경변수가 치환되지 않았다 (%q)", field, raw)
}
```

### 4. 테스트가 30초 걸렸다

`TestSendNeverBlocks` 는 "Send 가 안 막힌다"를 즉시 확인하는데
정리 단계에서 30초를 잡아먹었다. 1시간짜리 느린 채널을 큐에 넣어 뒀더니,
`Close()` 후 남은 이벤트마다 기본 발송 시한(10초)을 다 기다린 것이다.

검증 대상과 무관한 대기라 그 테스트에서만 시한을 50ms 로 줄였다.
**24초 → 4초.** 테스트를 느리게 두면 결국 안 돌리게 된다.

## 보안 메모

웹훅 URL 자체가 인증 수단이다. 유출되면 누구나 그 채널에 글을 쓸 수 있다.
그래서 설정 파일에는 환경변수 참조만 적는다.

```yaml
alerts:
  # discord_webhook: ${UPCHECK_DISCORD_WEBHOOK}
```

`.gitignore` 에 `configs/*.local.yaml` 이 이미 들어 있다.

## 스펙 요구사항 점검

| 요구 | 상태 |
|------|------|
| 상태 전이에만 발송 | 관문 2 — `confirmed` vs `notified` |
| 플래핑 방지 (연속 N회) | 관문 1 — `FailureThreshold`, 기본 3회 |
| 쿨다운 | 관문 3 — 기본 5분, 억제 시 알림을 미루고 잃지 않음 |
| `Notifier` 인터페이스 | 스펙 시그니처 그대로 |
| Discord / Slack 웹훅 | 공통 `webhook` + payload 함수 |
| 발송이 체크 루프를 막지 않음 | 논블로킹 `Send` + 별도 goroutine |
| down 정확히 1회 / up 1회 | 실측 확인 + `TestDownThenUpSendsExactlyOnce` |
| 플래핑에 알림 폭탄 없음 | 실측 3건/60초 + `TestFlappingDoesNotStorm` |
| `incidents` 테이블 채우기 | `OpenIncident` / `ResolveIncident` |
| `go test -race ./...` | 통과 |
