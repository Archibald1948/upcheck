# 09 — 데이터베이스 (database/sql · SQLite)

`internal/store/` 를 옆에 켜 두고 읽으면 좋다.

## database/sql 은 드라이버가 아니다

Go의 `database/sql` 은 **인터페이스만** 정의한다. 실제 DB와 말하는 건 드라이버다.
그래서 둘 다 import 해야 한다.

```go
import (
    "database/sql"
    _ "modernc.org/sqlite"
)
```

`_` 를 붙인 import 를 **blank import** 라고 한다.
이 패키지의 함수를 직접 부르진 않지만, 패키지의 `init()` 함수가
`sql.Register("sqlite", ...)` 를 실행해주는 게 목적이다.
`_` 없이 쓰면 "안 쓰는 import" 컴파일 에러가 난다.

### 왜 modernc.org/sqlite 인가

| | `mattn/go-sqlite3` | `modernc.org/sqlite` |
|---|---|---|
| 구현 | C 라이브러리 바인딩 | **C를 Go로 기계 번역한 순수 Go** |
| cgo | 필요 | 불필요 |
| 크로스 컴파일 | 타깃별 C 툴체인 필요 | `GOOS=linux go build` 한 방 |
| 속도 | 조금 빠름 | 조금 느림 |

`CGO_ENABLED=0` 으로 정적 바이너리를 만들 수 있다는 게 결정적이다.
"바이너리 하나 던져 놓으면 끝"이라는 Go의 장점을 지킬 수 있고,
M6의 distroless 도커 이미지도 여기에 달려 있다.

## Open 은 연결하지 않는다

```go
db, err := sql.Open("sqlite", dsn)   // 에러가 없어도 아직 연결 안 됐다
if err := db.PingContext(ctx); err != nil {  // 여기서 처음 연결한다
    return nil, fmt.Errorf("DB 연결 실패: %w", err)
}
```

`sql.Open` 은 이름 그대로 '여는' 게 아니라 **커넥션 풀 객체를 만들 뿐**이다.
실제 연결은 첫 질의 때 생긴다. 시작 시점에 설정이 틀린 걸 알고 싶으면
`Ping` 을 명시적으로 불러야 한다.

`*sql.DB` 는 커넥션 하나가 아니라 **풀**이다. 그래서
- 여러 goroutine 이 동시에 써도 안전하다
- 함수마다 열고 닫는 게 아니라 **프로그램 수명 내내 하나**를 들고 쓴다

## SQLite 특유의 것들

### 1. 날짜/시간 타입이 없다

TEXT(ISO8601) / INTEGER(epoch) / REAL(율리우스일) 중 하나를 골라야 한다.
upcheck 는 **INTEGER epoch 초(UTC)** 를 쓴다.

```sql
checked_at INTEGER NOT NULL
```

이유는 롤업 때문이다. 시간 버킷 계산이 나눗셈 한 번으로 끝난다.

```sql
SELECT monitor_id, checked_at / 3600 * 3600 AS hour   -- 정수 나눗셈 = 정시로 내림
FROM checks GROUP BY monitor_id, hour
```

TEXT 였다면 `strftime` 으로 잘라 붙여야 하고, 문자열 연산이라 인덱스도 잘 안 탄다.

Go 쪽에서는 변환 함수를 하나씩 두고 그것만 쓴다.

```go
func unix(t time.Time) int64      { return t.UTC().Unix() }
func fromUnix(sec int64) time.Time { return time.Unix(sec, 0).UTC() }
```

**저장은 항상 UTC**다 (스펙 7절 함정). 타임존은 화면에 그릴 때만 붙인다.
사람이 볼 때는 `datetime(checked_at, 'unixepoch')` 로 변환한다.

### 2. BOOLEAN 이 없다

0/1 정수로 저장한다. 그래서 이런 SQL 이 성립한다.

```sql
SELECT COUNT(*), COALESCE(SUM(ok), 0) FROM checks WHERE ...
```

`SUM(ok)` 가 곧 성공 개수다. 업타임 계산이 한 줄로 끝난다.

### 3. 타입이 느슨하다

SQLite 는 컬럼 타입이 '선호'일 뿐 다른 타입도 들어간다(동적 타입).
그래서 `NOT NULL`, `CHECK`, 외래키 같은 제약을 스키마에 확실히 걸어야 한다.

### 4. 외래키가 기본으로 꺼져 있다

```go
q.Add("_pragma", "foreign_keys(1)")
```

호환성 때문에 기본값이 off 다. 안 켜면 `REFERENCES` 를 써도 검사하지 않는다.
`TestForeignKeysEnabled` 로 켜져 있는지 고정해 뒀다.

### 5. 쓰기는 한 번에 하나뿐

DB 전체에 쓰기 잠금이 하나다. 이게 스펙 7절 함정이고, 두 가지로 대응한다.

**WAL 모드**
```go
q.Add("_pragma", "journal_mode(WAL)")
```
기본 모드에서는 쓰기가 읽기를 막는다. 집계 질의를 도는 동안 저장이 멈춘다는 뜻이다.
WAL 은 변경분을 별도 파일에 쌓아서 **읽기와 쓰기가 서로를 막지 않는다.**
(쓰기끼리는 여전히 하나씩이다)

**busy_timeout**
```go
q.Add("_pragma", "busy_timeout(5000)")
```
잠겨 있을 때 즉시 `database is locked` 로 실패하지 말고 기다리라는 뜻이다.
이게 없으면 재시도 로직을 직접 짜야 한다.

**커넥션 1개**
```go
db.SetMaxOpenConns(1)
```
커넥션을 여러 개 둬도 쓰기는 하나만 되고 나머지는 잠금을 기다린다.
우리는 쓰기가 collector goroutine 하나뿐이라(스펙 5절 구조) 1로 두는 게 깔끔하다.

> **PRAGMA 는 연결마다 걸린다.** `*sql.DB` 는 풀이라서, 한 커넥션에서
> 실행한 PRAGMA 가 다른 커넥션에는 적용되지 않는다. 그래서 코드 안에서
> `db.Exec("PRAGMA ...")` 를 부르는 대신 **연결 문자열에 넣는다.**
> 드라이버가 새 커넥션마다 다시 실행해준다.

### 6. DELETE 해도 파일이 안 줄어든다

지운 자리는 '빈 공간'으로 표시될 뿐 파일 크기는 그대로다.
실제로 반납하려면 `VACUUM` 을 돌려야 한다.

여기에 WAL 이 겹치면 헷갈리는 일이 생긴다. 실제로 겪은 것:

```
정리 후 : 2400행 · 16.7 MB     ← 144000행(13.0 MB)보다 커졌다?!
```

원인은 **WAL 파일을 같이 쟀기 때문**이다. VACUUM 이 만든 변경분이
아직 `-wal` 에 쌓여 있었다. 본 파일에 반영하고 WAL 을 비운 뒤 다시 재야 한다.

```sql
PRAGMA wal_checkpoint(TRUNCATE)
```

그랬더니 **7.5 MB → 0.1 MB**. 측정 대상이 틀렸던 것이지 코드가 틀린 게 아니었다.

## 질의하는 세 가지 방법

```go
// 1) 행 하나 — QueryRow
var n int64
err := db.QueryRowContext(ctx, `SELECT COUNT(*) FROM checks`).Scan(&n)

// 2) 여러 행 — Query
rows, err := db.QueryContext(ctx, `SELECT id, name FROM monitors`)
defer rows.Close()
for rows.Next() { ... }
if err := rows.Err(); err != nil { ... }

// 3) 결과가 없는 것 — Exec
res, err := db.ExecContext(ctx, `DELETE FROM checks WHERE checked_at < ?`, cutoff)
n, _ := res.RowsAffected()
```

`...Context` 가 붙은 쪽을 쓴다. ctx 가 취소되면 질의도 끊긴다 (→ [07](07-context.md)).

### rows 를 다룰 때 빠뜨리기 쉬운 두 가지

```go
rows, err := db.QueryContext(ctx, ...)
if err != nil { return err }
defer rows.Close()          // ① 안 닫으면 커넥션이 반납되지 않는다

for rows.Next() {
    if err := rows.Scan(&a, &b); err != nil { return err }
}
if err := rows.Err(); err != nil {   // ② 순회 중 난 에러
    return err
}
```

②가 특히 중요하다. `rows.Next()` 가 false 를 반환한 이유는
"데이터가 끝나서"일 수도 있고 "**에러가 나서**"일 수도 있다.
`rows.Err()` 를 안 보면 중간에 끊긴 결과를 완전한 것으로 착각한다.

커넥션이 1개인 우리 설정에서는 `rows.Close()` 를 빠뜨리면 **바로 교착**이다.
다음 질의가 커넥션을 영원히 기다린다.

### 플레이스홀더

```go
db.QueryContext(ctx, `SELECT * FROM checks WHERE monitor_id = ?`, id)   // O
db.QueryContext(ctx, `SELECT * FROM checks WHERE monitor_id = `+id)     // X SQL 인젝션
```

값은 **반드시** `?` 로 넘긴다. 단, **테이블명과 컬럼명은 플레이스홀더로 못 넘긴다.**
그건 문자열로 조립할 수밖에 없으니 반드시 화이트리스트에서만 고른다.

개수가 가변인 `IN` 절은 `?` 를 개수만큼 만들어 붙인다.

```go
q := "UPDATE monitors SET enabled = 0 WHERE name NOT IN (" + string(placeholders) + ")"
tx.ExecContext(ctx, q, names...)   // names 는 []any
```

### NULL 다루기

```go
var resolvedAt sql.NullInt64
rows.Scan(&resolvedAt)
if resolvedAt.Valid { ... }
```

NULL 이 들어올 수 있는 컬럼을 `int64` 로 Scan 하면 에러가 난다.
그래서 upcheck 스키마는 대부분 `NOT NULL DEFAULT` 를 걸어 NULL 자체를 피한다.
`incidents.resolved_at` 만 "아직 진행 중"을 나타내야 해서 NULL 을 허용한다.

`COALESCE(x, 기본값)` 로 SQL 쪽에서 미리 없애는 방법도 많이 쓴다.

```sql
SELECT COALESCE(SUM(total), 0) FROM checks_hourly WHERE ...
```

집계 함수는 **행이 하나도 없으면 NULL** 을 준다. `SUM` 이 0을 줄 거라 믿으면 안 된다.

### 행이 없는 건 에러가 아니다

```go
err := db.QueryRowContext(ctx, ...).Scan(...)
if err == sql.ErrNoRows {
    return nil, nil     // "아직 체크 안 함" — 정상 상태다
}
if err != nil {
    return nil, fmt.Errorf("최근 체크 조회 실패: %w", err)
}
```

`QueryRow` 는 행이 없으면 `sql.ErrNoRows` 를 준다.
이걸 다른 에러와 섞어 다루면 "데이터가 없음"이 "장애"로 둔갑한다.

## 트랜잭션

```go
func (s *Store) tx(ctx context.Context, fn func(*sql.Tx) error) error {
    tx, err := s.db.BeginTx(ctx, nil)
    if err != nil {
        return fmt.Errorf("트랜잭션 시작 실패: %w", err)
    }
    defer tx.Rollback()

    if err := fn(tx); err != nil {
        return err
    }
    return tx.Commit()
}
```

Go에는 `try/finally` 가 없어서 "성공하면 커밋, 아니면 롤백"을 매번 손으로 쓰면
어느 분기에서 빠뜨리게 된다. **함수를 인자로 받아** 감싸두면 호출부는 본문만 쓰면 된다.

```go
return s.tx(ctx, func(tx *sql.Tx) error {
    // 여기서 뭘 하든 커밋/롤백은 알아서 된다
})
```

`defer tx.Rollback()` 을 무조건 거는 게 요령이다. **이미 커밋된 트랜잭션에
Rollback 을 불러도 `sql.ErrTxDone` 이 날 뿐 해가 없다.** 그래서 조건 없이 걸어두면
어느 경로로 빠져나가도 정리된다.

### 배치 저장이 훨씬 빠른 이유

```go
// 느림: 행마다 트랜잭션 → 행마다 디스크 동기화
for _, r := range rows { db.Exec(`INSERT ...`, ...) }

// 빠름: 한 트랜잭션 → 동기화 한 번
s.tx(ctx, func(tx *sql.Tx) error {
    stmt, _ := tx.PrepareContext(ctx, `INSERT ...`)
    defer stmt.Close()
    for _, r := range rows { stmt.ExecContext(ctx, ...) }
    return nil
})
```

명시적 트랜잭션 없이 `Exec` 를 부르면 SQLite 가 **호출마다 트랜잭션을 열고 닫는다.**
커밋마다 디스크 동기화가 일어나서, 행이 많아지면 차이가 수십 배로 벌어진다.
실측으로 14만 행을 622ms 에 넣었다.

### Prepared Statement

같은 SQL 을 여러 번 실행할 때만 이득이다. SQL 파싱과 실행 계획 수립을 한 번만 한다.
한 번 쓰고 말 질의는 그냥 `Exec`/`Query` 가 낫다.

```go
stmt, err := tx.PrepareContext(ctx, `INSERT INTO checks ... VALUES (?, ?, ?, ?, ?, ?)`)
defer stmt.Close()   // 안 닫으면 커서가 남는다
```

## upsert — 있으면 갱신, 없으면 삽입

```sql
INSERT INTO monitors (name, target, ...) VALUES (?, ?, ...)
ON CONFLICT(name) DO UPDATE SET
    target = excluded.target,
    ...
RETURNING id
```

- `ON CONFLICT(name)` — `name` 의 UNIQUE 제약이 걸릴 때
- `excluded.컬럼` — 넣으려다 충돌한 **새 값**
- `RETURNING id` — 삽입이든 갱신이든 그 행의 id 를 돌려준다.
  덕분에 "넣고 나서 다시 SELECT" 하는 왕복을 없앤다.

## 인덱스

```sql
CREATE INDEX idx_checks_monitor_time ON checks(monitor_id, checked_at);
```

**복합 인덱스는 컬럼 순서가 전부다.** 이 인덱스는
- `WHERE monitor_id = ?` → 쓴다
- `WHERE monitor_id = ? AND checked_at BETWEEN ? AND ?` → 쓴다 (우리 질의 대부분)
- `WHERE checked_at > ?` → **못 쓴다** (앞 컬럼을 건너뛸 수 없다)

그래서 정리 잡이 쓰는 `WHERE checked_at < ?` 용으로 별도 인덱스를 하나 더 뒀다.

계획을 확인하려면:
```sql
EXPLAIN QUERY PLAN SELECT ... ;
```

### WITHOUT ROWID

```sql
CREATE TABLE checks_hourly (
    ...
    PRIMARY KEY (monitor_id, hour)
) WITHOUT ROWID;
```

SQLite 는 보통 숨은 `rowid` 를 실제 키로 쓰고 PK 는 별도 인덱스로 만든다.
`WITHOUT ROWID` 를 붙이면 PK 자체가 저장 순서가 되어 **중복 인덱스가 사라진다.**
`(monitor_id, hour)` 로만 접근하는 이 테이블에 딱 맞는다.

## 마이그레이션 (goose)

스키마를 코드로 관리한다. `goose_db_version` 테이블이 "지금 몇 번까지 적용됐는지"를
기억해서, 이미 적용된 건 건너뛴다. 프로그램을 몇 번 재시작해도 안전하다.

```sql
-- +goose Up
-- +goose StatementBegin
CREATE TABLE monitors ( ... );
-- +goose StatementEnd

-- +goose Down
-- +goose StatementBegin
DROP TABLE monitors;
-- +goose StatementEnd
```

주석처럼 생긴 `-- +goose` 가 지시문이다. Up 은 올릴 때, Down 은 되돌릴 때 실행된다.

### embed 로 바이너리에 넣기

```go
//go:embed migrations/*.sql
var migrationsFS embed.FS
```

`//go:embed` 는 **바로 아래 변수**에 파일 내용을 채워 넣으라는 컴파일러 지시문이다.
덕분에 SQL 파일을 따로 들고 다닐 필요 없이 바이너리 하나로 배포된다.

주의할 점:
- `//go:embed` 앞에 **공백이 있으면 안 된다** (`// go:embed` 도 안 됨)
- 바로 다음 줄이 변수 선언이어야 한다
- `embed` 패키지를 import 해야 한다 (`embed.FS` 를 안 써도 `_ "embed"` 로라도)

```go
goose.SetBaseFS(migrationsFS)
goose.SetLogger(goose.NopLogger())   // stdout 오염 방지
goose.SetDialect("sqlite3")
goose.Up(s.db, "migrations")
```

### 마이그레이션 규칙

- **이미 배포된 마이그레이션은 절대 고치지 않는다.** 새 파일을 추가한다.
  남의 DB 는 이미 그 버전을 적용했다고 기록해 뒀으므로 고쳐도 다시 안 돈다.
- 파일명은 번호가 앞에 온다: `00001_init.sql`, `00002_add_x.sql`
