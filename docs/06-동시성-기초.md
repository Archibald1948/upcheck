# 06 — 동시성 기초

Go의 동시성은 **goroutine** 과 **channel** 두 가지가 전부다.
`internal/scheduler/` 를 옆에 켜 두고 읽으면 좋다.

## goroutine

함수 앞에 `go` 를 붙이면 별도 실행 흐름으로 떨어져 나간다.

```go
go func() {
    defer close(jobs)
    p.schedule(ctx, monitors, jobs)
}()
```

`go` 문은 **즉시 반환**한다. 안의 함수가 끝나기를 기다리지 않는다.

### 스레드와 뭐가 다른가

| | OS 스레드 | goroutine |
|---|---|---|
| 초기 스택 | 1~8MB (고정) | 2KB (필요하면 늘어남) |
| 생성 비용 | 커널 호출, 수십 μs | 수백 ns |
| 전환 | 커널이 결정 | Go 런타임이 결정 |
| 몇 개까지 | 수천 개면 부담 | 수십만 개도 가능 |

Go 런타임이 goroutine 수만 개를 OS 스레드 몇 개 위에 얹어서 돌린다.
스레드 수는 기본적으로 CPU 코어 수(`GOMAXPROCS`)다.

**하지만 싸다고 무제한으로 만들면 안 된다.** goroutine 자체는 싸도
각각이 잡는 자원(HTTP 커넥션, 소켓, 상대 서버의 부하)은 싸지 않다.
이게 스펙 5절 규칙 3번이고, `TickerScheduler` 를 채택하지 않은 이유다.

### main 이 끝나면 다 죽는다

`main` 이 반환하면 남은 goroutine 은 정리 기회 없이 사라진다.
그래서 "모든 작업이 끝났다"를 확인하는 장치가 따로 필요하다.

## channel

goroutine끼리 값을 주고받는 통로다.

```go
jobs := make(chan Job, p.workers*2)   // 버퍼 있음
results := make(chan checker.Result)  // 버퍼 없음 (언버퍼)

jobs <- job        // 보내기
job := <-jobs      // 받기
job, ok := <-jobs  // ok == false 면 채널이 닫혔고 값도 다 떨어졌다
close(jobs)        // 닫기
```

> **"메모리를 공유해서 통신하지 말고, 통신해서 메모리를 공유하라"**
> — Go의 유명한 표어. 뮤텍스로 공유 변수를 지키는 대신
> 값을 채널로 넘겨 소유권을 옮긴다.

### 버퍼 크기를 어떻게 정하나

| 버퍼 | 동작 | 쓸 곳 |
|------|------|------|
| 0 (언버퍼) | 받는 쪽이 준비될 때까지 보내는 쪽이 멈춘다 | 확실한 인계, 신호 |
| N | N개까지는 안 멈추고 넣을 수 있다 | 순간적인 몰림 흡수 |

버퍼는 **순간적인 불균형을 흡수하는 용도**지, 처리 속도 차이를 메우지 못한다.
생산이 소비보다 계속 빠르면 아무리 큰 버퍼도 결국 찬다.

upcheck 의 선택:

```go
jobs := make(chan Job, p.workers*2)
```

워커 수의 2배다. 근거는 이렇다.
- **0이면** 스케줄러가 워커를 붙잡을 때까지 멈춰 서서, 그동안 다른 모니터의 예정 시각이 밀린다.
- **너무 크면** 오래된 작업이 큐에 쌓인다. 모니터링에서 30초 전에 예약된 체크를
  지금 실행하는 건 의미가 없다. **큐가 길다는 건 곧 측정값이 낡았다는 뜻이다.**
- 워커 수의 2배면 "모든 워커가 일하는 중 + 다음 차례 한 벌"이 들어간다.

### 닫는 규칙

1. **보내는 쪽이 닫는다.** 받는 쪽이 닫으면 보내는 쪽이 닫힌 채널에 보내다 panic 한다.
2. **두 번 닫으면 panic.**
3. **닫힌 채널에서 받기는 계속 된다** — 제로값과 `ok == false` 를 준다.

`Pool.Run` 이 이 규칙을 어떻게 지키는지 보자.

```go
// jobs 는 스케줄러만 보낸다 → 스케줄러가 닫는다
go func() {
    defer close(jobs)
    p.schedule(ctx, monitors, jobs)
}()

// results 는 워커들이 보낸다 → 전부 끝난 뒤에 닫아야 한다
go func() {
    wg.Wait()
    close(results)
}()
```

보내는 쪽이 **여럿**이면 아무도 혼자 닫을 수 없다. 그래서 `WaitGroup` 으로
전부 끝나기를 기다린 뒤 닫는 goroutine 을 따로 둔다. 아주 흔한 패턴이다.

### 채널 방향

```go
func (p *Pool) worker(ctx context.Context, id int,
    jobs <-chan Job,              // 수신 전용
    results chan<- checker.Result, // 송신 전용
)
```

`<-chan` 은 받기만, `chan<-` 은 보내기만 할 수 있다.
방향을 타입으로 제한하면 실수를 **컴파일러가** 잡아준다.
워커가 실수로 `jobs` 를 닫으려 하면 컴파일이 안 된다.

## select

여러 채널을 동시에 기다린다. 준비된 게 여럿이면 **무작위로** 하나를 고른다.

```go
select {
case <-ctx.Done():
    return
case job, ok := <-jobs:
    if !ok {
        return
    }
    ...
}
```

### default — 논블로킹

`default` 가 있으면 준비된 채널이 없을 때 기다리지 않고 바로 지나간다.

```go
select {
case jobs <- Job{Monitor: m, Due: d.due}:
    p.counters.scheduled.Add(1)
default:
    // 큐가 가득 찼다 = 워커가 전부 바쁘다
    p.counters.deferred.Add(1)
}
```

이게 **백프레셔(backpressure)** 처리다. 여기서 그냥 기다리면 스케줄러가
멈춰 서서 다른 모니터까지 전부 밀린다. 넣을 수 없으면 미루고 넘어간다.

### 두 개를 잇는 관용구

"일하다가 종료 신호가 오면 즉시 빠져나온다"는 거의 항상 이 모양이다.

```go
select {
case <-ctx.Done():
    return
case <-ticker.C:
}
```

`ticker.C` 만 기다렸다면 종료까지 최대 tick 만큼 늦어진다.

**보낼 때도 마찬가지다.** 이걸 빠뜨리는 게 goroutine 누수의 1번 원인이다.

```go
select {
case results <- res:
case <-ctx.Done():
    return
}
```

소비자가 사라졌는데 `results <- res` 로 그냥 보내면 버퍼가 차는 순간
이 goroutine 이 **영원히** 멈춘다.

## sync.WaitGroup

"N개가 다 끝날 때까지 기다린다".

```go
var wg sync.WaitGroup
for i := range p.workers {
    wg.Add(1)
    go func() {
        defer wg.Done()   // 어떻게 끝나든 반드시 감소
        p.worker(ctx, i, jobs, results)
    }()
}
wg.Wait()
```

규칙:
- `Add` 는 **goroutine 을 띄우기 전에** 부른다. 안에서 부르면 `Wait` 이 먼저 지나갈 수 있다.
- `Done` 은 `defer` 로 건다. panic 이 나도 카운터가 남지 않는다.
- `WaitGroup` 을 복사하면 안 된다. 넘길 땐 포인터로.

### WaitGroup vs errgroup

스펙 5절 다이어그램에는 `errgroup` 이 적혀 있는데 이 프로젝트는 `WaitGroup` 을 썼다. 이유:

| | `sync.WaitGroup` | `errgroup.Group` |
|---|---|---|
| 어디 | 표준 라이브러리 | `golang.org/x/sync` |
| 에러 | 다루지 않음 | 첫 에러를 모아준다 |
| 취소 | 직접 | `WithContext` 로 첫 에러 시 전체 취소 |
| 동시 수 제한 | 직접 | `SetLimit(n)` |

**errgroup 이 맞는 경우**: 여러 작업 중 하나라도 실패하면 전부 접어야 할 때.
예를 들어 M2에서 DB 마이그레이션 여러 개를 병렬로 돌린다면 errgroup 이 맞다.

**여기서 WaitGroup 이 맞는 이유**: 워커는 **실패하지 않는다.**
체크 실패는 `Result.Err` 에 담기는 **데이터**지 워커의 에러가 아니다
(→ [04-에러-처리.md](04-에러-처리.md)). 모니터 하나가 죽었다고 나머지 감시를
멈추면 그건 모니터링 도구가 아니다. 모을 에러가 없으니 errgroup 은 군더더기다.

> `errgroup.SetLimit(n)` 으로도 동시성을 제한할 수 있다. 다만 그건
> "작업 N개를 동시에 M개씩" 이고, 우리가 필요한 건
> "**영구히 도는** 워커 N개 + 작업 큐" 라서 워커풀이 더 맞다.

## sync.Mutex

채널로 안 되는 것도 있다. 공유 상태를 여럿이 읽고 쓸 때다.

```go
type Pool struct {
    mu       sync.Mutex
    inflight map[string]struct{}
}

func (p *Pool) acquire(name string) bool {
    p.mu.Lock()
    defer p.mu.Unlock()
    if _, busy := p.inflight[name]; busy {
        return false
    }
    p.inflight[name] = struct{}{}
    return true
}
```

**맵은 동시 접근에 안전하지 않다.** 두 goroutine 이 동시에 쓰면
Go 런타임이 `concurrent map writes` 로 프로그램을 죽인다.
(데이터가 조용히 깨지는 것보다 낫다는 판단이다)

- `Lock`/`Unlock` 은 항상 짝. `defer` 로 걸면 빠뜨릴 수 없다.
- 잠근 구간은 **짧게**. HTTP 요청 같은 걸 잠금 안에서 하면 안 된다.
- `sync.RWMutex` 는 읽기가 압도적으로 많을 때만 이득이다.

## sync/atomic

숫자 하나를 여럿이 건드릴 때는 뮤텍스보다 가볍다.

```go
type counters struct {
    scheduled atomic.Int64
    deferred  atomic.Int64
}

c.scheduled.Add(1)
c.scheduled.Load()
```

**`x++` 는 원자적이지 않다.** "읽고 → 더하고 → 쓰기" 세 단계라서
그 사이에 다른 goroutine 이 끼어들면 증가가 사라진다.

### CAS 루프

"읽고 비교해서 더 크면 쓴다"처럼 여러 단계가 필요하면 CAS 를 쓴다.

```go
func (c *counters) observeLag(lag time.Duration) {
    ns := int64(lag)
    for {
        cur := c.maxLagNS.Load()
        if ns <= cur {
            return
        }
        if c.maxLagNS.CompareAndSwap(cur, ns) {
            return
        }
        // 실패 = 그 찰나에 누가 바꿨다. 다시 읽고 재시도.
    }
}
```

`CompareAndSwap(old, new)` 는 "값이 **아직** old 일 때만 new 로 바꾸고 true".
경쟁에서 지면 false 가 오고, 다시 읽어서 시도한다.

## data race와 `-race`

두 goroutine 이 같은 메모리를 동시에 건드리고 그중 하나가 쓰기면 **data race** 다.
결과는 정의되지 않는다. 값이 깨지거나, 안 깨지거나, 특정 머신에서만 깨진다.

```bash
go test -race ./...
```

`-race` 를 켜면 런타임이 모든 메모리 접근을 감시해서 race 를 잡아낸다.
**느려지지만(5~10배) CI 에는 반드시 넣어야 한다** (스펙 5절 규칙 4번).

중요한 한계: **실제로 실행된 코드 경로만** 잡는다. 테스트가 그 조합을
안 돌리면 못 찾는다. 그래서 `TestCountersAreRaceFree` 같은
"일부러 동시에 두들기는" 테스트가 필요하다.

## goroutine 누수 4가지 패턴

스펙 9절이 묻는 것이다. 누수 = **영원히 끝나지 않는 goroutine**.
goroutine 은 GC 대상이 아니라서, 막힌 채로 두면 그 스택과 참조가 영원히 남는다.

### 1. 아무도 받지 않는 채널에 보내기

```go
ch := make(chan int)      // 언버퍼
go func() { ch <- 1 }()   // 받는 사람이 없으면 영원히 멈춤
return                    // 이 goroutine 은 영원히 산다
```
**탐지**: 스택에 `chan send` 가 쌓인다.
**대응**: 보낼 때도 `select` 에 `ctx.Done()` 을 같이 둔다.

### 2. 닫히지 않는 채널에서 받기

```go
for v := range ch { ... }   // ch 를 아무도 close 하지 않으면 영원히 대기
```
**탐지**: 스택에 `chan receive`.
**대응**: 보내는 쪽이 반드시 닫는다. 또는 `select` 로 `ctx.Done()` 을 같이 본다.

### 3. `context.WithCancel` / `WithTimeout` 의 cancel 미호출

```go
ctx, cancel := context.WithTimeout(ctx, d)
// defer cancel() 을 빠뜨림 → 내부 타이머와 goroutine 이 남는다
```
**탐지**: `go vet` 이 잡아준다 (`lostcancel`).
**대응**: 얻는 즉시 `defer cancel()`.

### 4. `time.Ticker` 를 `Stop` 하지 않음

```go
ticker := time.NewTicker(d)
// defer ticker.Stop() 을 빠뜨림 → 런타임 타이머가 계속 남는다
```
**대응**: `defer ticker.Stop()`.
(`time.After` 를 루프 안에서 쓰는 것도 같은 이유로 위험하다.
시한이 찰 때까지 타이머가 안 사라진다)

### 탐지하는 법

```bash
# 종료 후 남은 goroutine 스택 보기
go run ./cmd/upcheck -duration 10s -dump-goroutines

# 테스트로 검증 (internal/scheduler/scheduler_test.go)
go test -race -run TestNoGoroutineLeak ./internal/scheduler/ -v
```

운영 중에는 M6에서 붙일 `/debug/pprof/goroutine` 으로 본다.
**숫자가 계속 우상향하면 누수다.**

Go 1.27 에는 `/debug/pprof/goroutineleak` 프로파일이 새로 들어왔는데,
"도달 불가능한(아무도 깨워줄 수 없는) goroutine"만 추려준다.
직접 세는 것보다 판정이 훨씬 명확하다. M6에서 붙인다.
