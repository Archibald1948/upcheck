구조는 이렇게 이어진다.

```
scheduler → results ─┬→ collector → 배치 → SQLite
                     └→ (M3) 상태 전이 판정 → 알림
```

자연스럽게 한 goroutine 으로 직렬화된다 (스펙 7절 함정).
따로 뮤텍스를 걸거나 쓰기 큐를 만들 필요가 없었다.

## 설계 결정

### 1. 시각을 INTEGER epoch 로 저장한 이유

SQLite 에는 날짜 타입이 없어서 TEXT / INTEGER / REAL 중 골라야 한다.
INTEGER(UTC epoch 초)를 골랐다. **롤업 때문**이다.

```sql
SELECT monitor_id, checked_at / 3600 * 3600 AS hour   -- 정수 나눗셈 = 정시로 내림
FROM checks GROUP BY monitor_id, hour
```

시간 버킷 계산이 나눗셈 한 번이다. TEXT 였다면 `strftime` 으로 잘라 붙여야 하고,
문자열 연산이라 인덱스도 잘 안 탄다. 이 질의는 롤업 때마다 도는 핵심 경로다.

읽기 어려운 건 `datetime(checked_at, 'unixepoch')` 로 해결한다.

### 2. 업타임은 정확, 응답시간은 근사

롤업에서 제일 중요한 성질이다.

**개수는 합쳐도 정확하다.** `total`, `ok_count` 는 더하면 그대로다.
그래서 원본을 다 지운 뒤에도 30일 업타임이 **정확히** 같은 값이다.
`TestUptimeSurvivesPrune` 이 이걸 고정한다 — 288행을 지우고도 87.5000% 유지.

**백분위수는 합칠 수 없다.** p95 들의 평균은 전체의 p95 가 아니다.
칸마다 히스토그램이나 t-digest 를 저장하면 정확해지지만, 이 규모에서는 과하다.

그래서 **근사라는 사실을 값에 담아** 전달한다.

```go
type Latency struct {
    P50, P95, Max time.Duration
    Samples       int64
    Approx        bool   // ← 롤업에서 근사한 값이면 true
}
```

`-report` 출력에도 표시한다.

```
※ p50/p95 중 일부는 시간별 롤업에서 근사한 값이다.
  백분위수는 합칠 수 없어서, 원본이 정리된 구간은 정확하지 않다.
  업타임 %는 개수 합이라 롤업 구간도 정확하다.
```

숫자만 보여주고 말면 사용자가 정확한 값이라고 믿는다. 그게 더 나쁘다.

### 3. 롤업과 원본을 잇는 경계

같은 구간을 두 테이블에서 읽으면 중복이 나고, 잘못 나누면 누락이 난다.
경계를 **롤업이 끝난 지점** 하나로 정했다.

```go
func (s *Store) rollupFrontier(ctx context.Context) (int64, error) {
    var frontier int64
    err := s.db.QueryRowContext(ctx,
        `SELECT COALESCE(MAX(hour) + 3600, 0) FROM checks_hourly`).Scan(&frontier)
    ...
}
```

- 이 시각 **앞**은 `checks_hourly` 에서 읽는다
- 이 시각 **뒤**는 `checks` 에서 읽는다

"정시 기준"이 아니라 "실제로 롤업이 끝난 지점" 기준인 게 중요하다.
정리 잡이 아직 안 돌았으면 완료된 시간도 원본에만 있는데,
정시를 경계로 삼으면 그 구간을 통째로 놓친다.

`COALESCE(..., 0)` 덕분에 롤업이 한 번도 안 돌았으면 경계가 0이라
자연스럽게 전부 원본에서 읽는다.

`TestUptimeExactAcrossSeam` 이 롤업 전후의 업타임이 **소수점까지 같은지** 검사한다.

> 남은 오차: 구간 시작이 정시가 아니면 첫 칸에 `since` 이전 데이터가
> 최대 59분까지 섞인다. 24시간/7일/30일 구간에서는 무시할 만해서 그대로 뒀다.

### 4. 실패한 체크는 응답시간에서 뺀다

```sql
SELECT latency_ms FROM checks WHERE ... AND ok = 1
```

실패 체크의 '응답시간'은 대부분 **타임아웃까지 걸린 시간**이다.
5초 타임아웃 하나가 섞이면 p95 가 5000ms 로 튄다.
"서비스가 살아 있을 때 얼마나 빠른가"를 재는 지표라 성공만 센다.
`TestLatencyIgnoresFailedChecks` 로 고정.

### 5. 설정에서 사라진 모니터를 지우지 않는다

```sql
UPDATE monitors SET enabled = 0 WHERE name NOT IN (...)
```

`ON DELETE CASCADE` 가 걸려 있어서 모니터를 지우면 과거 체크 기록까지 날아간다.
YAML 에서 한 줄 지웠다고 몇 달 치 이력이 사라지면 곤란하다. 비활성화만 한다.

## 부딪힌 것들

### 1. 종료 시 마지막 배치를 잃을 뻔했다

collector 는 결과를 모아서 한 번에 저장한다. 그런데 Ctrl+C 를 누르면
**ctx 가 이미 취소된 상태**로 채널이 닫힌다. 그 ctx 로 저장을 시도하면
질의가 즉시 실패해서 배치가 통째로 사라진다.

```go
case res, ok := <-results:
    if !ok {
        // ctx 는 이미 죽었다. 새 시한을 판다.
        flushCtx, cancel := context.WithTimeout(context.Background(), finalFlushTimeout)
        defer cancel()
        c.flush(flushCtx, batch)
        return nil
    }
```

`context.Background()` 에서 새로 시작하는 게 요점이다. 취소된 ctx 의
자식을 만들면 그 자식도 태어나자마자 취소되어 있다.

`TestCollectorFlushesOnCancelledContext` 가 **이미 취소된 ctx** 를 넘겨
이 경로를 직접 검증한다. M2에서 데이터를 잃기 제일 쉬운 지점이었다.

정리 잡도 같은 처리를 한다 — 종료 직전에 마지막 구간을 한 번 더 접는다.

### 2. 정리했더니 파일이 커졌다

스케일 테스트를 처음 돌렸을 때:

```
원본      :  144000행 ·  13.0 MB
정리 후   :    2400행 ·  16.7 MB     ← ?!
```

`VACUUM` 까지 돌렸는데 파일이 커졌다. 원인은 **WAL 파일을 같이 쟀기 때문**이다.
VACUUM 이 만든 변경분이 아직 `-wal` 에 쌓여 있었다. 본 파일은 줄었는데
WAL 이 부푼 상태로 합산한 것이다.

```sql
PRAGMA wal_checkpoint(TRUNCATE)   -- WAL 내용을 본 파일에 반영하고 WAL 을 비운다
```

체크포인트 후 다시 재니 **7.5 MB → 0.1 MB**.
코드가 틀린 게 아니라 **측정이 틀렸던** 경우다. WAL 모드에서 파일 크기를
잴 때는 항상 체크포인트를 먼저 해야 한다.

### 3. 집계 안 된 원본을 지울 뻔했다

정리 잡이 "보관 기간 지난 원본 삭제"만 보면, 롤업이 아직 안 돈 구간도 지운다.
그 데이터는 영영 사라진다. M2에서 제일 위험한 지점이다.

```go
var rolledUpTo int64
tx.QueryRowContext(ctx, `SELECT COALESCE(MAX(hour) + 3600, 0) FROM checks_hourly`).Scan(&rolledUpTo)
cutoff := min(rawCutoff, rolledUpTo)   // 둘 중 이른 쪽까지만 지운다
```

그리고 `Maintain` 이 **Rollup → Prune 순서를 강제**한다.
호출부가 순서를 헷갈릴 여지를 없앴다.

`TestPruneWaitsForRollup` 이 "롤업 없이 정리만 시도하면 한 행도 안 지운다"를 검사한다.

## 다음: M3

알림이다. 여기서 `incidents` 테이블이 채워진다.

- **상태 전이에만** 발송 (up→down, down→up)
- **플래핑 방지**: 연속 N회 실패해야 down 확정 (기본 3회)
- **쿨다운**: 같은 모니터에 X분 내 재발송 금지
- `Notifier` 인터페이스로 Discord / Slack 추상화

판정 로직이 들어갈 자리는 이미 준비돼 있다 — `Collector.Run` 의 `onResult` 훅이다.
`cmd/slowserver` 의 `/flaky`(3초 주기로 200↔503)가 플래핑 테스트용으로 대기 중이다.

알림 발송이 체크 루프를 막으면 안 되므로(스펙 7절 함정),
별도 goroutine + 버퍼 채널로 띄워야 한다.
