# 04 — 에러 처리

Go에는 예외(exception)가 없다. **에러는 그냥 값**이고, 다른 반환값처럼 다룬다.

## 기본 형태

```go
func Load(path string) (*Config, error)
```

관례:
- `error` 는 **마지막 반환값**
- 에러가 있으면 다른 반환값은 **믿으면 안 된다** (보통 nil/제로값)
- 호출부는 **즉시** 검사한다

```go
cfg, err := config.Load(*configPath)
if err != nil {
    return err
}
```

## 에러 만들기

```go
errors.New("모니터가 하나도 없다")                    // 고정 문구
fmt.Errorf("monitors[%d]: name 이 비어 있다", i)      // 값을 끼울 때
fmt.Errorf("설정 파일 읽기 실패: %w", err)             // 다른 에러를 감쌀 때
```

### 에러 메시지 규칙

- **소문자로 시작하고 마침표를 안 찍는다.** 상위에서 감싸면서
  `"A 실패: B 실패: 원본 에러"` 처럼 이어 붙기 때문이다.
  (한글은 대소문자가 없으니 마침표만 신경 쓰면 된다)
- **"failed to" 같은 말을 반복하지 않는다.** 어차피 에러라는 건 이미 안다.
- **문맥을 더한다.** 어느 파일인지, 어느 모니터인지.
  ```go
  return fmt.Errorf("%s: target 이 비어 있다", m.Name)
  ```

## `%w` — 에러 감싸기

`%w` 로 감싸면 **원본 에러가 안에 보존**된다. `%v` 로 하면 문자열만 남고 사라진다.

```go
data, err := os.ReadFile(path)
if err != nil {
    return nil, fmt.Errorf("설정 파일 읽기 실패: %w", err)
}
```

출력은 이렇게 이어진다.
```
오류: 설정 파일 읽기 실패: open configs/없다.yaml: no such file or directory
```

감쌌기 때문에 나중에 **원본을 꺼내 판단**할 수 있다.

### errors.Is — 특정 에러인지

```go
if errors.Is(err, os.ErrNotExist) {
    // 파일이 없는 경우만 다르게 처리
}
if errors.Is(err, context.DeadlineExceeded) {
    // 타임아웃
}
```

`==` 로 비교하면 안 된다. 감싸져 있으면 못 찾는다. `errors.Is` 는
감싼 껍질을 **끝까지 벗겨가며** 비교한다.

### errors.As — 특정 타입으로 꺼내기

```go
var urlErr *url.Error
if errors.As(err, &urlErr) {
    fmt.Println(urlErr.URL, urlErr.Timeout())
}
```

에러 안의 추가 정보(어느 URL이었는지 등)가 필요할 때 쓴다.

## 센티널 에러

패키지가 미리 정의해 둔 특정 에러 값이다.

```go
var ErrMonitorNotFound = errors.New("모니터를 찾을 수 없다")

// 쓰는 쪽
if errors.Is(err, ErrMonitorNotFound) { ... }
```

이름은 `Err` 로 시작하는 게 관례다. 표준 라이브러리의 `io.EOF`,
`sql.ErrNoRows`, `os.ErrNotExist` 가 전부 이 방식이다.

## 실제 예: checker의 에러 분류

`internal/checker/checker.go` 를 보자.

```go
func classifyErr(ctx context.Context, err error) error {
    switch ctx.Err() {
    case context.DeadlineExceeded:
        return fmt.Errorf("타임아웃")
    case context.Canceled:
        return fmt.Errorf("취소됨(종료 중)")
    }
    return err
}
```

`http.Client.Do` 가 실패하면 에러 문자열이 이렇게 길다.

```
Get "https://x.com": context deadline exceeded
```

그런데 "**타임아웃이라 실패**"와 "**Ctrl+C 눌러서 취소됨**"은 의미가 전혀 다르다.
앞은 진짜 장애고 뒤는 우리가 끈 것이다. `ctx.Err()` 로 **왜 끊겼는지**를
물어보면 둘을 구분할 수 있다.

> `ctx.Err()` 는 context가 아직 살아 있으면 `nil`, 취소됐으면
> `context.Canceled`, 시한이 지났으면 `context.DeadlineExceeded` 를 반환한다.

### 에러를 Result에 담는 이유

checker는 에러를 **반환하지 않고** `Result` 구조체에 담는다.

```go
type Result struct {
    Monitor    string
    OK         bool
    StatusCode int
    Latency    time.Duration
    Err        error        // ← 여기
}

func (c *Checker) Check(ctx context.Context, m config.Monitor) Result
```

모니터링 도구에서 "체크 실패"는 **예외 상황이 아니라 정상적인 결과**다.
엔드포인트가 죽은 건 우리가 알아내려던 바로 그 사실이다.
그래서 에러를 데이터로 취급해서 DB에 저장하고 통계를 낸다. (M2에서 쓴다)

Go에서 `error` 반환은 "이 함수가 **자기 할 일을 못 했다**"는 뜻으로 남겨둔다.

## panic과 recover

**거의 쓰지 않는다.** panic은 프로그램을 죽인다.

자동으로 panic이 나는 경우:
- nil 포인터 역참조
- 슬라이스 범위 초과 (`s[10]` 인데 길이가 3)
- nil 맵에 쓰기
- 실패하는 타입 단언 (`x.(T)`)
- 0으로 나누기

직접 `panic()` 을 부르는 건 **프로그래머의 버그**로 복구 불가능할 때뿐이다.
예: 프로그램 시작 시 반드시 있어야 할 리소스가 없을 때.

`recover()` 로 잡을 수 있지만, `defer` 안에서만 동작한다.

```go
func safeCheck() (err error) {
    defer func() {
        if r := recover(); r != nil {
            err = fmt.Errorf("패닉 복구: %v", r)
        }
    }()
    ...
}
```

M1에서 워커 goroutine을 짤 때 이 패턴이 쓸모 있다.
**goroutine 하나에서 난 panic은 프로그램 전체를 죽이기 때문**에,
워커 안에서 잡아주면 모니터 하나가 이상해도 데몬이 살아남는다.

## os.Exit과 defer

```go
func main() {
    if err := run(); err != nil {
        fmt.Fprintf(os.Stderr, "오류: %v\n", err)
        os.Exit(1)
    }
}
```
→ `cmd/upcheck/main.go`

로직을 `run()` 으로 뺀 이유가 있다. **`os.Exit` 은 defer를 실행하지 않는다.**
main 안에서 바로 `os.Exit(1)` 을 부르면 열어둔 파일, DB 연결,
`defer cancel()` 이 전부 무시된 채 죽는다.

`run() error` 로 분리해 두면 run이 정상 반환하면서 defer가 다 돌고,
그 다음에 main이 종료 코드를 정한다. **Go에서 아주 흔한 관용구다.**

## 무시해도 되는 에러

```go
_, _ = io.Copy(io.Discard, resp.Body)
defer resp.Body.Close()
```

`_ =` 를 명시하면 "실수가 아니라 일부러 무시했다"는 신호가 된다.
`defer resp.Body.Close()` 처럼 defer에 붙은 것도 에러를 버리는데,
읽기 전용 응답에서는 관례적으로 허용된다.
(파일을 **쓰는** 경우엔 `Close()` 에러를 반드시 확인해야 한다.
버퍼가 flush되지 않아 데이터가 날아갈 수 있다)

`errcheck`, `go vet` 같은 도구가 무시한 에러를 잡아준다.
