# 15 — 관측과 배포 (지표 · 프로파일 · 도커)

`internal/metrics/`, `internal/admin/`, `Dockerfile` 을 옆에 켜 두고 읽으면 좋다.

## 로그 · 지표 · 프로파일은 서로 다른 도구다

| | 무엇을 답하나 | 언제 보나 |
|---|---|---|
| **로그** | "그때 무슨 일이 있었나" | 사건 하나를 파고들 때 |
| **지표** | "요즘 어떤 추세인가" | 대시보드·알림 |
| **프로파일** | "지금 왜 이렇게 느리고 무거운가" | 성능 문제를 쫓을 때 |

알림이 "지금 죽었다"를 알려준다면 지표는 "요즘 느려지고 있다"를 보여준다.
셋 다 있어야 한다.

## Prometheus 지표

### 네 가지 타입

| 타입 | 쓸 곳 | 예 |
|---|---|---|
| Counter | **줄지 않는** 누적값 | 체크 횟수, 알림 발송 수 |
| Gauge | 오르내리는 현재값 | 모니터 상태, goroutine 수 |
| Histogram | 값의 분포 | 응답시간 |
| Summary | 분위수를 클라이언트가 계산 | (대개 Histogram 을 쓴다) |

**Counter 와 Gauge 를 구분하는 건 취향이 아니다.** Prometheus 는 카운터에만
`rate()` 를 쓸 수 있고, 카운터 값이 줄어들면 "프로세스가 재시작했다"로 해석해
그 구간을 보정한다. 누적 횟수를 게이지로 내보내면 그 계산이 전부 틀어진다.

### 전역 레지스트리를 쓰지 않는다

```go
m := &Metrics{reg: prometheus.NewRegistry()}
m.reg.MustRegister(m.checksTotal, ...)
```

`prometheus.MustRegister(...)` 는 전역 레지스트리에 등록한다. 편하지만
**같은 지표를 두 번 등록하면 panic** 이라, 테스트를 두 개만 돌려도 깨진다.
레지스트리를 직접 만들면 테스트마다 새 것을 쓰면 그만이다.

```go
mux.Handle("GET /metrics", promhttp.HandlerFor(s.registry, promhttp.HandlerOpts{...}))
```

### 라벨은 곱해진다 — 카디널리티

```go
prometheus.NewCounterVec(opts, []string{"monitor", "type", "result"})
```

시계열 개수 = 모니터 수 × 타입 수 × 결과 수. 모니터 1000개여도 수천 개다.

**넣으면 안 되는 라벨**: URL 전체, 에러 메시지, 사용자 ID, 타임스탬프.
값의 가짓수가 무한히 늘어나 Prometheus 의 메모리를 먹어치운다.
이걸 카디널리티 폭발이라고 하고, 모니터링 시스템이 죽는 가장 흔한 이유다.

### 이미 세고 있는 값은 복사하지 않는다

스케줄러·collector·알림 엔진은 이미 자기 통계를 세고 있다.
같은 값을 지표 객체에 또 쌓으면 두 벌이 어긋난다.

```go
func (m *Metrics) AddCounter(name, help string, fn func() float64) {
    m.reg.MustRegister(prometheus.NewCounterFunc(
        prometheus.CounterOpts{Name: name, Help: help}, fn,
    ))
}

// 쓰는 쪽
m.AddCounter("upcheck_checks_scheduled_total", "...",
    func() float64 { return float64(sched.Stats().Scheduled) })
```

Prometheus 가 긁어갈 때마다 `fn` 이 불린다. 덕분에 `metrics` 패키지가
`scheduler` 를 import 하지 않아도 된다 — 의존 방향이 한쪽으로만 흐른다.

### 함정: 스크레이프는 다른 goroutine 이다

`fn` 은 HTTP 핸들러 goroutine 에서 불린다. 그 값을 쓰는 쪽은 collector
goroutine 이다. 평범한 `int64` 였다면 **data race** 다.

M6에서 `collector` 와 `alert.Engine` 의 통계를 `atomic.Int64` 로 바꾼 이유다.
M2·M3 당시에는 "Run 이 끝난 뒤에만 읽는다"는 전제로 평범한 int 를 썼는데,
`/metrics` 가 그 전제를 깼다. `go test -race` 가 있어서 바로 드러난다.

### 무엇을 재나

실패한 체크의 응답시간은 히스토그램에 **넣지 않는다.**
대부분 타임아웃까지 걸린 시간이라 분위수를 왜곡한다.
(M2에서 p50/p95 를 성공만으로 계산한 것과 같은 이유 → [10](10-M2-저장과집계.md))

```go
if res.OK {
    m.checkDuration.WithLabelValues(res.Monitor, res.Type).Observe(res.Latency.Seconds())
}
```

Go 런타임 지표는 공짜로 따라온다.

```go
m.reg.MustRegister(
    collectors.NewGoCollector(),                                    // go_goroutines, 힙, GC
    collectors.NewProcessCollector(collectors.ProcessCollectorOpts{}), // CPU, 열린 fd, RSS
)
```

`go_goroutines` 하나로 스펙 6절의 "goroutine 수가 증가하지 않음"을
그래프로 감시할 수 있다.

## 헬스체크 — liveness 와 readiness 는 다르다

| | 실패하면 | 무엇을 확인하나 |
|---|---|---|
| `/healthz` (liveness) | 컨테이너를 **재시작** | 프로세스가 응답하는가 |
| `/readyz` (readiness) | 트래픽만 **뺀다** | 실제로 일할 수 있는가 |

**liveness 에서 DB를 확인하면 안 된다.** DB가 잠깐 느려서 liveness 가 실패하면
오케스트레이터가 컨테이너를 재시작하고, 재시작하면 연결이 더 몰려서 더 느려진다.
장애를 스스로 증폭시키는 고전적인 실수다.

```go
func (s *Server) handleHealthz(w http.ResponseWriter, r *http.Request) {
    writeJSON(w, http.StatusOK, s.snapshot("ok", ""))   // DB 를 보지 않는다
}

func (s *Server) handleReadyz(w http.ResponseWriter, r *http.Request) {
    ctx, cancel := context.WithTimeout(r.Context(), 2*time.Second)
    defer cancel()
    if err := s.ready.Ping(ctx); err != nil { ... 503 ... }
}
```

readiness 에도 **짧은 시한**을 건다. 확인이 길어지면 헬스체크 자체가 부하가 된다.

에러 원문은 응답에 싣지 않고 로그에만 남긴다. `no such table: monitors` 같은
메시지는 내부 구조를 알려준다 (→ [14](14-M5-API와-상태페이지.md)의 정보 노출).

### 버전을 -ldflags 없이 얻기

```go
info, _ := debug.ReadBuildInfo()
for _, s := range info.Settings {
    switch s.Key {
    case "vcs.revision": ...
    case "vcs.modified": ...
    }
}
```

Go 는 빌드할 때 모듈 정보와 (git 저장소에서 빌드했다면) 커밋 해시·dirty 여부를
바이너리에 넣어 둔다. `-ldflags "-X main.version=..."` 로 주입하지 않아도 된다.

```
{"status":"ok","version":"5a9f52b-dirty","uptime_sec":4,"goroutines":26}
```

> 도커 빌드에서는 `.dockerignore` 가 `.git` 을 빼므로 `(devel)` 로 나온다.
> 커밋 해시가 필요하면 `.git` 을 포함시키거나 빌드 인자로 넘겨야 한다.

## pprof

```go
mux.HandleFunc("GET /debug/pprof/", pprof.Index)
mux.HandleFunc("GET /debug/pprof/profile", pprof.Profile)
...
```

| 프로파일 | 답하는 질문 |
|---|---|
| `goroutine` | 지금 goroutine 이 어디서 멈춰 있나 |
| `goroutineleak` | **아무도 깨워줄 수 없는** goroutine 이 있나 (Go 1.27 신규) |
| `heap` | 메모리를 누가 잡고 있나 |
| `allocs` | 할당을 누가 많이 하나 |
| `profile` | CPU 를 어디서 쓰나 (기본 30초 수집) |

```bash
go tool pprof -http=: http://127.0.0.1:8485/debug/pprof/heap
curl "http://127.0.0.1:8485/debug/pprof/goroutineleak?debug=1"
```

`goroutineleak` 은 스펙 3절이 짚은 Go 1.27 의 새 프로파일이다.
전체 goroutine 목록에서 눈으로 "이건 정상, 이건 이상"을 가리는 대신,
**도달 불가능한 것만** 추려 준다. 판정이 훨씬 명확하다.

### 함정 1: import 만으로 전역 mux 에 등록된다

`net/http/pprof` 의 `init()` 은 이렇게 생겼다.

```go
func init() {
    http.HandleFunc("GET /debug/pprof/", Index)
    ...
}
```

`http.HandleFunc` 는 **DefaultServeMux** 에 등록한다. blank import 든 아니든,
패키지를 import 하는 순간 벌어지는 일이라 막을 수 없다.
(테스트를 쓰다가 확인했다 — `TestPprofNotExposedByPublicAPI`)

그러니 규칙은 **"어디서도 DefaultServeMux 를 서비스하지 않는다"** 이다.

```go
http.ListenAndServe(addr, nil)   // ← nil 이면 DefaultServeMux. pprof 가 통째로 열린다
http.Server{Handler: myMux}      // ← 항상 핸들러를 명시한다
```

### 함정 2: 공개 포트에 두면 안 된다

프로파일에는 힙 내용과 모든 goroutine 스택이 들어간다. 처리 중이던 요청 데이터나
설정값이 그대로 보일 수 있다. CPU 프로파일은 30초 동안 서버를 붙잡는다.

upcheck 는 운영 엔드포인트를 **다른 포트**에 두고 기본 주소를 `127.0.0.1` 로 한다.

### 함정 3: WriteTimeout 이 프로파일보다 짧으면 안 된다

```go
WriteTimeout: 65 * time.Second,   // CPU 프로파일 기본 30초 + 여유
```

공개 API 는 30초로 충분하지만, 운영 서버를 같은 값으로 두면 CPU 프로파일이
항상 중간에 끊긴다.

## 도커 — 멀티스테이지와 distroless

```dockerfile
FROM golang:1.27-alpine AS build
...
RUN CGO_ENABLED=0 GOOS=linux go build -trimpath -ldflags="-s -w" -o /out/upcheck ./cmd/upcheck

FROM gcr.io/distroless/static-debian12:nonroot
COPY --from=build /out/upcheck /usr/local/bin/upcheck
```

빌드 단계에는 Go 툴체인(수백 MB)이 있지만 최종 이미지에는 바이너리만 남는다.
**27MB** 가 나왔다.

### CGO_ENABLED=0 이 전부를 가능하게 한다

C 라이브러리에 링크하지 않은 **정적 바이너리**가 나와서, libc 조차 없는
`distroless/static` 에서 그대로 돈다.

M2에서 `modernc.org/sqlite`(순수 Go)를 고른 결정이 여기서 값을 한다
(→ [09](09-데이터베이스.md)). `mattn/go-sqlite3` 였다면 cgo 가 필요해서
`distroless/base` 나 alpine 을 써야 하고, 크로스 컴파일도 번거로워진다.

### distroless 에는 아무것도 없다

셸도, 패키지 매니저도, `mkdir` 도, `curl` 도 없다. 그래서 생기는 일들:

**① 디렉터리를 미리 만들어 둬야 한다**

```dockerfile
RUN mkdir -p /data && chown 65532:65532 /data      # 빌드 단계에서
COPY --from=build --chown=65532:65532 /data /data  # 최종 이미지로
```

도커는 **빈 볼륨을 처음 붙일 때** 이미지의 해당 디렉터리 내용과 소유권을
볼륨으로 복사한다. 그래서 이렇게 해두면 비루트 사용자가 SQLite 파일을 만들 수 있다.

**② 헬스체크를 바이너리가 스스로 한다**

```dockerfile
HEALTHCHECK CMD ["/usr/local/bin/upcheck", "-healthcheck", "-admin", "127.0.0.1:8485"]
```

흔히 쓰는 `curl -f .../healthz` 를 쓸 수 없다. 프로그램에 모드를 하나 두면
이미지를 살찌우지 않고 해결된다. 도커는 **종료 코드**로만 판단한다.

**③ 시간대 데이터가 없다**

```go
import _ "time/tzdata"
```

`time.LoadLocation("Asia/Seoul")` 은 보통 OS 의 `/usr/share/zoneinfo` 를 읽는다.
distroless 에는 그 파일이 없어서 **도커에서만** 실패한다.
이 import 한 줄이 시간대 DB 를 바이너리에 넣는다 (약 450KB).

로컬에서는 멀쩡하고 컨테이너에서만 깨지는 종류라, 미리 넣어 두는 게 낫다.

### ENTRYPOINT 는 exec 형식으로

```dockerfile
ENTRYPOINT ["/usr/local/bin/upcheck"]      # exec 형식 — upcheck 가 PID 1
ENTRYPOINT /usr/local/bin/upcheck          # 셸 형식 — /bin/sh 가 PID 1
```

셸 형식은 `/bin/sh -c "..."` 로 감싸서 **셸이 PID 1** 이 된다. 셸은 SIGTERM 을
자식에게 전달하지 않아서, `docker stop` 이 10초를 기다렸다가 SIGKILL 로 죽인다.
우아한 종료를 아무리 잘 짜도 무의미해진다.
(distroless 에는 `/bin/sh` 가 아예 없어서 셸 형식은 실행조차 안 된다)

실측: `docker compose stop` 이 **1.44초**에 끝나고 종료 코드가 0이다.
컨테이너 로그에 종료 요약까지 찍힌다.

### 레이어 캐시 — 변하지 않는 것부터

```dockerfile
COPY go.mod go.sum ./
RUN go mod download        # 의존성이 그대로면 이 레이어는 재사용
COPY . .
RUN go build ...
```

소스만 고쳤을 때 의존성을 다시 받지 않는다. Node 쪽도 같은 이유로
`package-lock.json` 만 먼저 복사해 `npm ci` 를 돌린다.

`npm ci` 는 `npm install` 과 달리 lock 파일을 고치지 않아서 빌드가 재현 가능하다.

### Next.js standalone

```ts
const nextConfig: NextConfig = { output: "standalone" };
```

실행에 필요한 파일만 추린 `server.js` 와 최소 `node_modules` 가 나온다.
전체 `node_modules`(수백 MB)를 옮기지 않아도 된다.

## compose — 무엇을 공개할지 정하는 자리

```yaml
services:
  upcheck:
    expose: ["8484", "8485"]       # 내부 네트워크에만
  web:
    ports: ["3000:3000"]           # 호스트에 공개
    depends_on:
      upcheck:
        condition: service_healthy
```

`expose` 는 컨테이너끼리만 보이게 하고, `ports` 는 호스트로 내보낸다.
Go API 와 운영 포트는 호스트에서 **연결조차 되지 않는다.**

M5에서 브라우저가 Go API 를 직접 부르지 않게 만든 덕분에 가능한 구성이다
(→ [14](14-M5-API와-상태페이지.md)).

`condition: service_healthy` 는 헬스체크가 통과할 때까지 web 을 띄우지 않는다.
없으면 첫 화면이 "API 에 연결할 수 없습니다"로 뜬다.

### 환경변수는 실행 시점에

```yaml
environment:
  UPCHECK_API_URL: http://upcheck:8484    # compose 내부 DNS = 서비스 이름
```

Next.js 의 `NEXT_PUBLIC_` 변수는 **빌드 시점에 JS 번들에 박힌다.** 그걸 썼다면
이미지 하나를 개발·스테이징·운영에 쓸 수 없다. 서버에서만 읽는 변수로 두면
실행할 때 정해진다.
