# 00 — 환경과 도구

## 설치

```bash
brew install go
go version   # go version go1.27.1 darwin/arm64
```

설치 용량은 **약 270MB**(`/opt/homebrew/Cellar/go`). Go는 상주 데몬이 없어서
평소 메모리를 전혀 쓰지 않고, `go build` / `go test` 를 돌릴 때만
수백 MB를 썼다가 끝나면 반납한다.

쓰다 보면 두 개의 캐시가 쌓인다.

| 경로 | 내용 |
|------|------|
| `~/Library/Caches/go-build` | 빌드 캐시. 다시 빌드할 때 재사용해서 빨라진다 |
| `~/go/pkg/mod` | 내려받은 외부 라이브러리 원본 |

용량이 부담되면 `go clean -cache -modcache` 로 비운다. 지워도 다음 빌드 때 다시 만들어진다.

## 자주 쓰는 명령어

```bash
go run ./cmd/upcheck          # 빌드해서 바로 실행 (바이너리를 남기지 않음)
go build ./...                # 전체 컴파일. 에러만 확인하고 싶을 때
go build -o bin/upcheck ./cmd/upcheck   # 실행 파일 만들기
go test ./...                 # 전체 테스트
go test -race ./...           # 경쟁 상태(data race) 탐지기를 켜고 테스트
go vet ./...                  # 컴파일은 되지만 수상한 코드 찾기
gofmt -l .                    # 포맷이 어긋난 파일 나열 (-w 면 고침)
go mod tidy                   # 실제 import 에 맞춰 의존성 정리
go doc net/http.Client        # 터미널에서 문서 보기
```

`./...` 은 "현재 디렉터리 이하 모든 패키지"라는 뜻이다.

### gofmt은 논쟁이 없다

Go는 코드 스타일이 **언어 차원에서 하나로 고정**돼 있다. 들여쓰기는 탭,
중괄호 위치도 정해져 있고, `gofmt` 이 알아서 고친다.
파이썬의 black, JS의 prettier와 달리 설정할 게 아예 없다.
에디터에 "저장할 때 gofmt" 를 켜 두면 신경 쓸 일이 없어진다.

VS Code면 Go 확장(`golang.go`)을 설치하면 자동으로 붙는다.

## 모듈 (`go.mod`)

Go의 의존성 단위는 **모듈**이다. npm의 `package.json` 에 해당한다.

```bash
go mod init github.com/Archibald1948/upcheck
```

이 레포의 `go.mod`:

```
module github.com/Archibald1948/upcheck

go 1.27

require gopkg.in/yaml.v3 v3.0.1
```

- `module` 줄이 **import 경로의 뿌리**다. 그래서 내부 패키지를
  `github.com/Archibald1948/upcheck/internal/config` 로 import 한다.
  실제로 GitHub에 올라가 있을 필요는 없지만, 나중에 올릴 거라면
  처음부터 실제 주소로 맞춰두는 게 편하다.
- `go.sum` 은 내려받은 모듈의 해시다. 손대지 말고 커밋한다.
  누가 라이브러리를 몰래 바꿔치기하는 걸 막아준다.

### 의존성 추가

npm처럼 `install` 명령을 먼저 치지 않는다. **코드에 import 부터 쓰고**
`go mod tidy` 를 돌리면 알아서 찾아서 `go.mod` 에 적어준다.

```go
import "gopkg.in/yaml.v3"   // 이렇게 쓰고
```
```bash
go mod tidy                  # 이러면 내려받고 go.mod 에 기록됨
```

## 폴더 구조

```
upcheck/
├── go.mod
├── cmd/                  실행 파일들
│   ├── upcheck/          └ 본체
│   └── slowserver/       └ 테스트용 느린 서버
├── internal/             이 모듈 안에서만 import 가능한 패키지
│   ├── config/
│   └── checker/
├── configs/              YAML 설정
├── scripts/
└── docs/                 ← 지금 보고 있는 곳
```

두 가지가 Go의 관례다.

**`cmd/`** — `package main` 이면서 `func main()` 이 있는 패키지만 실행 파일이 된다.
실행 파일이 여러 개면 `cmd/<이름>/main.go` 로 나눈다.
바이너리 이름은 **폴더 이름**을 따라간다 (`cmd/upcheck` → `upcheck`).

**`internal/`** — Go 컴파일러가 특별 취급하는 이름이다.
`internal/` 아래 패키지는 **그 부모 디렉터리 밖에서 import 할 수 없다.**
남이 내 레포를 import 해도 `internal/checker` 는 못 건드린다.
공개 API와 내부 구현을 구분하는 장치다.

## 이름 규칙

Go에는 `public` / `private` 키워드가 없다. **식별자 첫 글자의 대소문자**가 그 역할을 한다.

```go
func Load(path string) (*Config, error)   // 대문자 → 패키지 밖에서 보임 (exported)
func (c *Config) applyDefaults() error    // 소문자 → 패키지 안에서만 (unexported)
```

구조체 필드도 똑같다. 그래서 JSON/YAML로 직렬화할 필드는 **반드시 대문자**여야 한다.
라이브러리가 리플렉션으로 읽는데, 소문자 필드는 아예 보이지 않기 때문이다.

```go
type Monitor struct {
    Name string `yaml:"name"`   // 대문자 O — yaml 이 읽을 수 있음
    name string `yaml:"name"`   // 소문자 X — 조용히 무시됨. 흔한 함정!
}
```

패키지 이름은 짧은 소문자 한 단어를 쓴다 (`config`, `checker`). 언더스코어나
카멜케이스를 쓰지 않는다. 그리고 패키지명이 이미 문맥을 주므로
`config.Config` 는 괜찮지만 `config.ConfigStruct` 처럼 반복하지 않는다.
